### ⭐ 为什么原始 JSON 用「外部内容」FTS

113 MB 的 JSON 全文如果既存表又建独立索引，会变成两份 → 库膨胀到 560 MB。
用 FTS5 的**外部内容模式**（`content='raw_json'`），索引只存倒排：

```sql
CREATE VIRTUAL TABLE raw_json_fts USING fts5(
    text, content='raw_json', content_rowid='rowid', tokenize='trigram');
```

省下约 113 MB，且检索行为不变。

### ⭐ 检索为什么要「两级降级」

SQLite 的 FTS5 **trigram 分词器要求查询词 ≥ 3 个字符**——查「玉琮」（2 字）会命中 0 条。
所以 `_match_lit_ids()` 的规则是：

- 全部词 ≥ 3 字 → 走 FTS5 索引
- **只要有一个词短于阈值** → 整条查询退回 `LIKE` 扫描

混合查询必须按「最长的短板」决定：半边走索引半边扫描会**漏结果**。
实测：2 字「玉琮」走 LIKE 命中 **67** 篇，3 字「良渚古城」走 FTS5 命中 **77** 篇。

### ⭐ 四维标签规范化：代码**不能**当聚合依据

登记表里的四维标签是「代码 + 名称」的复合串，多值用 `;` 分隔：

```
主题分类：S-0801 数据库; S-0803 GIS
空间分区：R-0101 良渚古城
文化谱系：良渚文化（数字展示）
```

规范化做了四件事（见 `lzkg/migrate.py: normalize_tags`）：

1. 拆多值（`；` `;` `、`）
2. 拆「代码 / 名称」：`R-0101 良渚古城` → code=`R-0101`, name=`良渚古城`
3. **括号限定后缀不进 name**：`良渚文化（数字展示）` → name=`良渚文化`，
   限定词只留在 `raw_forms` 里。（否则文化谱系会长出 17 个「良渚文化某某」伪实体。）
4. **受控词表归并**（`lzkg/vocab.py`）：同义归并 + 组合标签拆分
5. **唯一码位**（`data/controlled_vocab_codes.json`）：每个受控词一个唯一码

#### 为什么第 4、5 步是必需的（实测）

登记表里的「代码」**是族系代号，不是标签代号** —— 库里 **5 个码位下藏着 54 个不同的名称**：

| 维度 | 码位 | 名称数 | 例子 |
|---|---|---|---|
| topic | `S-0802` | 18 | 文物研究 / 治理路径 / 纹饰研究 / 聚落考古 / 学术史 / 植物考古 / 科技考古 / 宗教考古 / 丧葬考古 / 祭祀考古 / 建筑技术 / 玉器研究 / 墓葬考古 / 环境考古 / 水利工程 / 社会考古 / 人骨考古 / 水利与环境 |
| topic | `S-0801` | 11 | 数据库 / 考古发掘 / 保护 / 综述 / 考古研究 / 方法研究 / 空间分析 / 墓葬 / 祭坛遗址 / 玉器 / 遗址调查 |
| topic | `S-0803` | 9 | GIS / 数字化 / AIGC / 遥感 / VR / 数字传播 / 数字化保护 / 建筑研究 / 数字化传播 |
| region | `R-0199` | 8 | 浙江综合 / 中国综合 / 文化创意 / 良渚博物院 / 环太湖 / 良渚全域 / 数字化 / 良渚遗址群 |
| topic | `S-0804` | 8 | 活化 / 信息系统 / 人机共创 / 数字博物馆 / 公园 / 媒体研究 / 文创设计 / 产品开发 |

按代码归一会把「环太湖」和「文化创意」并成同一个东西、把「GIS」和「数字化保护」并成同一个东西。

**校准后的做法**（`lzkg/vocab.py`）：

- **唯一码位**：`S-0801~0804` / `R-0199` 这些族系代号**全部退役**，
  其下 54 个词各自拿到唯一码（新码段 `R-02xx` / `S-09xx`，一眼能看出是校准后新分配的）
- **同义归并**（人工审定的保守白名单，只合并确定等价的）：
  `墓葬→墓葬考古`、`玉器→玉器研究`、`建筑技术→建筑研究`、`数字化传播→数字传播`
- **组合标签拆分**：`凌家滩文化/红山文化` → 两个独立文化（斜杠是原表的写法，不是概念）
- **不合并的**：`数字化保护`、`水利与环境`、`吴越文化` —— 更具体或范围不同的独立概念，合了丢信息

实测结果：受控词 120 → **115** 条，`multi_semantics_codes` **清零**，
`region`/`topic` 两个维度每个受控词都有唯一码，`code_reliable=0` 的词 **0** 个。

> **图谱节点仍按「名称」建**（`tag_id = dim:name`），所以受控词表校准**不改变图谱语义**；
> 只有同义归并会真的减少节点（4 组等价词合并）。

### ⭐ 复核口径：有日期 ≠ 已复核

图像登记表里 `复核日期` **3 162 行全非空**（含未复核的行），
但 `复核人` 只有 214 行有值。所以：

- **判定「已复核」一律读 `review_status` 字段**，不用日期
- 已复核 619 / 待复核 2 516 / 其他 27 → **复核覆盖率 19.6%**
- 界面上这个数字直接标出来，并注明「复核日期非空不代表已复核」

## 四、图谱：L1 表派生，零抽取

**节点 4 类**：`lit` 文献 / `img` 图像 / `tag` 标签 / `objtype` 图像对象类型
**关系 5 类**：`contains` 文献→图像 / `depicts` 图像→对象 / `tagged` 文献→标签 /
`imgtag` 图像→标签 / `cocite` 文献↔文献（共享标签）

**全部由两张登记表 JOIN 得到，不做任何实体抽取**——所以没有误判，也没有「规则抽出的碎片」。

### 三条口径纪律（从 `cacx` 踩过的坑继承）

1. **筛选后的指标必须在筛选后的范围重算。** 分析与画图共用 `crop_scope()` 的输出，
   否则会出现「排名表跑全图、画的是子图」的两个数打架。
2. **Louvain 必须锁 `seed=42`。** 不锁的话每次社区划分都不同，截图对不上、报告数字不可复现。
   验收脚本里有「两次调用结果一致」这条判据。
3. **连通块数不等于质量。** 界面同时显示「实际返回节点/边数」与「筛选后总节点/边数」，
   截断时明确标注「已截断」。**把「图的样子」当成「现实的样子」是最容易犯的错。**

### 点边出证据

每条边都能点回原始文献：

- `contains` → 图注 + 图号 + 页码 + 图片路径
- `tagged` → 登记表原文（如 `S-0801 数据库; S-0803 GIS`）
- `cocite` → 双方共享的标签清单

### ⭐ 布局是**算好的**，不是每次打开重排的

vis-network 默认的力导向**每次打开都在重算**，节点位置会漂：同一份数据两次截图对不上，
报告里的图和演示时的图不是一张。而且本图密度是 600 节点 / 7 179 边（裁剪前），
力导向下缩成一团毛线，点都点不中。

所以坐标**后端一次算好**存进 `graph_nodes.x / y`，前端 `physics:false` 直接用坐标画。
算法（`lzkg/layout.py`）是**社区感知**的向日葵螺线排布：

1. Louvain 分簇（seed 固定，与图分析同一套参数）
2. 每簇在自己的诱导子图上跑 spring_layout
3. 簇之间沿**自适应螺线**外推，保证相邻簇不重叠
4. 全图归一到 `[-1000, 1000]`

**两个让「可复现」翻车的坑**（都不报错、同进程测两次还是绿的，
只在「重算一次后和库里的坐标对不上」才暴露）：

| 坑 | 机制 | 后果 |
|---|---|---|
| SQLite 无 `ORDER BY` 时**扫描顺序会变** | 优化器按统计信息在索引扫描与表扫描之间自选；而 Louvain / spring_layout **都对节点插入顺序敏感** | 社区从 9 个变 8 个，坐标最大差 **191** |
| Python `set` 迭代顺序受 `PYTHONHASHSEED` **随机化** | `G.subgraph(社区集合)` 按 set 顺序建图；spring_layout 按节点顺序分配初始随机位置 | 跨进程坐标不同 |

→ 修法：参与图算法的查询**一律写死 `ORDER BY`**；建诱导子图**显式按 node_id 排序**。
→ 验收判据在 `tests/test_all.py --layout`：**跨进程 + 换 `PYTHONHASHSEED`** 比对布局签名
（只写「同进程调两次一致」是**测不出上面两个坑**的）。
→ 实测：全新迁移出来的库与增量库的布局**完全一致** → 换个环境重建，图的画法一模一样。

### ⭐ 边必须给一条「列表通道」

600 节点 / 7 179 边缩到全图时连线只有十几像素，**点不中**。
所以图谱页左侧有 260px 的**边列表**：按源/目标/关系/节点名过滤，点一行看证据，
**最多渲染 300 行**（上千条全渲染会卡），底部写明「共 N 条，已显示前 300 条」
（N 是**当前返回的边数**，随裁剪结果变，不写死）。

### ⭐ 图谱降密度：实测基线与三处治法

用户反馈「图谱过于密集」。**先把「挤」量化**，再谈怎么改 ——
「看着挤」没法写进判据。

**基线**（600 节点 / 7 179 边 / 用全图坐标）：
**513 个（85%）节点的最近邻距离 < 20px**，中位只有 **8.8px**，最小 0（完全重合）；
而 11px 的标签字宽约 60px → **必然叠字**。

**三处根因，三处治法**（`lzkg/graphview.py`）：

| 根因 | 治法 | 实测 |
|---|---|---|
| 边全画 | **按度数上限裁边**（`trim_edges`，cap=6） | 7 179 → **1 012** 条；最大度数 263 → **12** |
| 坐标属全图 | **按裁剪后的子图重算布局**（`layout_subgraph`，spring seed=42，迭代 100，分位 clip 后归一化） | 最近邻中位 8.8px → **14.316px** |
| 标签全显示 | **标签给「社区代表」**（`label_candidates`，按社区轮转排序） | 43 个标签，前 12 个覆盖 **12** 个社区 |

三个反直觉的点（都是**实测推翻**的，写在这里免得下次又走回头路）：

1. **「每节点保 top-k 条」对 hub 无效** —— hub 有 300 个邻居，而每个邻居都把 hub
   当成自己最强的那条边 → hub 的边一条没少（实测裁完仍有 167 度）。
   必须用「**任何节点的度数都不得超过 cap**」。
2. **裁边后的孤点比边本身更难缠** —— cap=6 裁完 **43%** 的节点变成孤点（都是图版节点）。
   给孤点接「它最强的那条边」→ 几百个孤点全挂到同一个 `objtype:IMGOBJ-OTHER`，
   把那个节点撑到 **186 度**，cap 直接失效。
   → 孤点接「**当前度数最小**的邻居」，**并且接回也有上限**（对方 ≥ cap×2 就不接）。
   实测这一改让节点数/边数/最大度数/稀疏度**四项同时变好**（589→505 节点、
   1 096→1 012 边、19→12 度、13.38→14.32px）—— 限制不是妥协，是双赢。
3. **标签要给「社区代表」而不是「度数最高」** —— 度数最高的正是跨社区的 hub，
   全挤在簇心（度数 top60 两两最近距中位仅 **19.4px**）；社区代表是 **93.9px**。
   **标签要分散，不要集中在簇心。** 排序用**轮转**（社区1第一个、社区2第一个……），
   否则渐进披露的前 12 个只覆盖一半社区。

**前端配套**（`lzkg/web/static/index.html`）：
边淡色 + 取消平滑、节点按类型分级大小、标签白描边、
**标签按缩放渐进披露**（全图 12 → 中等 24 → 放大后 43）、
字号按缩放**反算补偿**（vis-network 的文字随 canvas 缩放，全图 scale 仅 0.25）。

★ 两个坑：渐进披露把 `label` 置空后**原值会丢** → 必须另存 `full_label`；
vis-network 的 `moveTo({scale})` **不触发** `zoom` 事件（实测 `fired=0`）
→ 程序化缩放要另加 **scale 轮询**兜底。

坐标仍由**后端**算（固定 seed、可复现），前端 `physics:false` ——
「同一份数据永远画出同一张图」这条不因为好看而丢掉。

## 四之二、导入导出与协作（工作台）

工作台是**扩展项**（课件第 13 页说「右边每加一项，都要有⼈长期维护」），
所以这里的每一项都设计成**不增加长期维护负担**：

### 导入是「提案—审核制」，不是直接改库

```
上传 xlsx  →  预检 diff  →  提案进 staging  →  管理员逐条批准  →  才写主库
```

- **按列名匹配**，不按列序：`32 列模板` 与 `34 列最终版` 都能吃
- 表头行**自动定位**（在前 10 行里按列名集合找最像表头的那行）
- 缺必填列 → 直接 400，说清缺哪几列；未知列 → 列出但不报错
- 每一行的改动都留痕：`old` / `new` / 谁提的 / 谁批的 / 什么时候
- 审批通过才落主库，并写 `import_log`

**为什么不是「上传即覆盖」**：登记表是教师发的、组员也在填。
谁在什么时候把哪一格改成了什么，必须能追回来。**已完成的审核记录不删，只改状态。**

### 单一事实来源：登记表列定义

`lzkg/schema/registry_columns.json` 定义 34 + 26 列（列名 / 是否必填 / 是否在精简模板内 /
帮助文字 / 示例）。**模板生成、迁移、导入预检、导出、录入表单**全部从它来。
改列只改这一个文件，**不要在别处硬编码列名**。

### 登录与权限：两道锁

- 密码哈希用 `hashlib.scrypt`（**标准库，零依赖**，比 PBKDF2 强）
- **界面层**：非管理员看不到「提案与审核」整块
- **接口层**：管理端点一律 `require_admin`，手动构造请求也只得到 403
- `config.json` 的 `auth.enabled=false`（默认）→ 全员免登录视为 admin，方便本机演示

### AI 问答：没配 key 就不装样子

`config.json` 的 `ai` 段配了 `api_base` / `api_key` / `model` 才走模型；
**没配就降级**成本地 FTS5 检索结果摘要，响应里 `degraded: true`，
并且页面上**显眼地标注**「未配置大模型，以下是本地检索结果，不是模型生成的回答」。

**不许编答案。** 宁可说「没配」，也不给一个看起来像模型说的、实际是拼凑的东西。

### ⭐ 「仅本机」这个锁，在隧道后面**等于没锁**

`/api/health/detail`、`/api/diagnose` 这类端点含**本机绝对路径**（库在哪、源数据在哪）。
原来的判断是 `request.client.host not in ("127.0.0.1","::1")` → 403。

**但在 Cloudflare Tunnel / 反向代理后面**，uvicorn 看到的直连方是**代理进程自己**
（隧道走本机回环）→ `client.host` **恒为 127.0.0.1**。
也就是说，这个锁**在真正需要它的场景下完全不生效**，公网访客能直接拿到本机路径。

现在的规则（`app.py` 的 `_is_local_request`）：

1. 直连方地址**必须**是回环地址
2. **且**没有转发头，或转发来的地址（`CF-Connecting-IP` / `X-Real-IP` / `X-Forwarded-For`）
   也是回环

→ 隧道进来的公网访客 → **403**；外网直连 → **403**；本机直接访问 → 放行。
→ 另加总闸：`config.json` 的 `app.local_detail`（默认 `true`），挂公网时置 `false` 整体关掉。

**怎么验**：跑 `python _tools/audit_exposure.py`，它做两遍探测——
普通匿名 + **「隧道视角」**（带 `CF-Connecting-IP: 203.0.113.7` 模拟经代理进来的访客）。
隧道视角下本机端点必须全部 401/403。实测：修之前 200（泄露绝对路径），修之后 403。

### 详情页的「地图标记」：内嵌小地图 + 分档标精度

文献详情页（`#/lit/LIT-xxxxxx`）有一块「**地图标记**」：
一个**聚焦到该点**的内嵌 Leaflet 小地图（底图仍是本地 GeoJSON，零联网），
下面配一段文字说明。

**为什么必须分档标精度**：坐标的精度差一个数量级 ——

| 档 | 含义 | 精度 |
|---|---|---|
| **文献坐标** | 坐标由文献给出；标 `from_this_paper` 区分「**本篇提供**」还是「他篇提供」 | 点级（米级） |
| **公开权威坐标** | 出处是公开权威资料（如良渚古城遗址整体） | 遗址整体（百米级） |
| **分区代表点** | 本篇带空间分区标签，落在分区代表点上 | **区块统一坐标，约 ±1.1 km**（不是实测坐标） |
| **未定位** | 没有可定位坐标 | —— |

把它们混画在图上、或者只写「有坐标」→ 读者会以为「**每篇文献都有一个精确位置**」，
那是骗人。所以每条标记都带：**精度说明 / 坐标 / 出处 / 坐标依据 / 命中依据**。

★ **不命中就是「未定位」，不推测填充**：小地图宁可**留空并写明原因**，
也不画一个假位置（「未定位不等于『在某个地方』」）。
★ **主题类分区不配点**（数字化 / 文化创意 / 参考案例 / 跨遗址）——
  给主题类分区一个点就是在编造位置。
★ 与「统计与地图」页**共用同一份关键词表**（`POINT_KEYS`，模块级），
  两边的关联口径不会各说各话。
★ 坐标一律 WGS84，**不用**高德/百度那套加密坐标冒充。

### Web Dev：把自己的浏览数据存下来

### 浏览数据：默认只在本机，开了同步才另存一份

**浏览记录默认只存在各自浏览器的 localStorage 里**（键 `lzkg.browse.v1`，上限 500 条），
此时后端一条都不存。**只有开了同步之后**，才会再存一份到你选的同步目标。

**同步目标有两条路，按「谁配了就用谁」选：**

| 目标 | 怎么配 | 数据在哪 | 换设备 |
|---|---|---|---|
| **本站服务器**（零配置） | 不用配，登录即用 | `data/record/<身份>/browse.json` | 登录就能取回 |
| **WebDAV** | 填地址 / 账号 / 应用授权密码 | 你自己的网盘 | 要重新填一次凭据 |

配了 WebDAV 就走网盘（你明确说过要存自己网盘，不该被服务器存储抢走），
没配就走本站服务器；两个都没有，右上角显示「同步：未设置」，**点它直接跳 `#/work/webdev`** 去配。

**右上角同步控件**（钉在顶栏，任何页面都看得见）：

- 主按钮 = 自动同步开关（`自动同步：开` / `关` / `同步中…` / `同步失败`）
- 「⟳ 立即同步」= 双向合并一次（下载 → 合并 → 上传，**两端收敛到并集**）
- 自动同步**只做上行**：浏览记录一变就排一次（**节流 2.5 秒 + 单飞**，连着看几篇只发一次）。
  双向收敛只放在手动同步里 —— 每次都先下载太慢，两台设备同时开着还容易互相覆盖。
- 状态/上次同步时间/失败原因存浏览器（键 `lzkg.autosync.v1`），刷新不丢。

Web Dev（WebDAV）配置也在浏览器里（键 `lzkg.webdav.v1`）：服务器地址、账号、
**应用授权密码**、文件名。配置区挂着两个说明链接：
[坚果云：第三方应用授权 WebDAV 开启方法](https://help.jianguoyun.com/?p=2064)、
[WebDAV 是什么 / 怎么用（知乎）](https://zhuanlan.zhihu.com/p/397069064)。

★ **为什么要后端代理**：浏览器直连 WebDAV 会被 **CORS** 挡死（WebDAV 服务默认不发 CORS 头），
只能由后端发请求。代价说清：**密码会随请求经过本站后端**再转发给你的 WebDAV 服务器，
后端**不落盘、不写日志、不回显**；且后端**只允许公网地址**（`lzkg/webdav.py` 有 SSRF 防护）。
★ 坚果云要用「第三方应用管理」里生成的**应用授权密码**，不是账号密码。

★ **坚果云的文件必须放在一个已存在的文件夹里** —— 直接往根目录写会返回 **404**。
所以配置里有「**存放目录**」（默认 `lzkg`），后端上传前会自动建出来；
「测试连接」测的也是**最终目标目录**，避免「测试通过、上传却 404」。

**「存服务器」这条路的安全边界**（全在 `lzkg/browserec.py`）：

- **各存各的目录**，目录名由后端从身份推导 —— 客户端传什么是进不去的（`../` 无效）
- 读接口只返回调用者自己那份，**没有「按用户名读别人」的入口**
- **只存白名单字段**（`kind/id/title/year/ts`）：就算客户端塞了 `password`、`token`，也进不了磁盘
- 单份上限 1 MB；**原子写**（`.tmp` → `os.replace`）；覆盖前留 `browse.prev.json`
- 管理员总闸 `config.browse_server.enabled`：关掉后接口一律 403

★ 还有一条完全离线、零依赖的路：**导出 JSON / 导入 JSON**（文件微信传给自己就行）。
★ Web Dev 另有总闸（`config.webdev.enabled`）：关掉后成员入口不渲染、接口一律 403；
各人的 WebDAV 凭据本来就在各自浏览器里，管理员看不到。

## 四之六、阅读原文通道 + XML 协作格式

> 用户需求原话：「建议文献界面给予阅读原文通道（PDF/Markdown），或许可以顺带这两个资源的下载，
> 这个功能可以与导入功能联动一下」，并选定「**两者都要**：交换用 XML，视图也提供 XML」。

### 1. 「阅读原文」：详情页一个模态窗口，两条通道

详情页（`#/lit/LIT-xxxxxx`）多了一块「**阅读原文**」，五个按钮：

| 按钮 | 端点 | 行为 |
|---|---|---|
| 📄 阅读 PDF | `GET /api/raw/{lit_id}/pdf` | 浏览器原生阅读器内嵌（`<iframe>`） |
| 📝 阅读 Markdown | `GET /api/raw/{lit_id}/markdown` | 后端渲染成安全 HTML 注入模态窗口 |
| ⬇ 下载 PDF | `?download=1` | 出附件（RFC 5987 编码中文文件名） |
| ⬇ 下载 Markdown | `?download=1` | 出附件 |
| 🧾 结构化 XML | `GET /api/literatures/{lit_id}/xml` | 新标签页打开单篇 XML |

**为什么 PDF 用 `<iframe>` 而不是 pdf.js**：本站**零外链**是硬约束，
pdf.js 体积大且要自己 vendor 化；浏览器原生 PDF 阅读器（Chromium 的 PDFium）
本来就支持内嵌、翻页、缩放、下载，零依赖、零外链。代价是 Firefox/Safari 的表现略有差异，
但**内嵌可用**这条已实测通过。

**Markdown 为什么在后端渲染**：前端做 Markdown 解析要引库（外链）或自己写（易漏 XSS）。
所以后端 `lzkg/rawtext.py` 把 MD 转成**白名单 HTML**：只放行 `sub/sup/i/b/em/strong`
这几个行内标签，其余全部转义。**前端不做任何解析，只做 `innerHTML` 注入**。

### 2. 图版重写：MinerU 的 CDN 直链换成站内图版

MinerU 解析出的 Markdown 里，图片是**外部 CDN 直链**
（`https://cdn-mineru.openxlab.org.cn/result/.../<hash>.jpg`）——断网就没图。
`map_md_images()` 把它们重写成本站 `/media/img/...` 的本地图版。

**重写规则（宁可留占位，绝不错配）**：

1. MD 里的图数**必须等于**库里这篇的图数（按 rowid 数），否则**整篇不重写**
2. 按**出现顺序**一一对应
3. 再做**图注文本校验**：MD 里的 alt 文字与库里的图注要能对上
4. 校验**明确不通过**的图 → 不重写，插一个占位提示

**实测真值（全库 200 篇）**：

| 情况 | 篇数 |
|---|---|
| MD 图数 == 库图数（可按序映射） | **50** |
| MD 图数 != 库图数（整篇不重写） | **17** |
| 无图 | **132** |
| `md_path` 文件名过长导致 Windows 路径解析不到 | **1**（LIT-000082） |

LIT-000001 实测：MD 14 张图 / 库 14 张 → **重写 12 张、未匹配 2 张**
（那 2 张的库 caption 被登记成了坐标文字，校验不过 → 留占位）。
渲染结果：12 个 `<img>`、0 字面 `![` 残留、2 个占位提示、**0 CDN 残留**。
图注校验整体命中率 **39.8%**（多数 MD 的 alt 只是文件名，不含图注文本）。

★ **校验不过就不重写**——把 A 图错配给 B 图是**造谣**，比缺图严重得多。

### 3. XML：一套格式，两处用

`lzkg/xmlexchange.py`，命名空间 `urn:lzkg:literature:1`（不是 http:// 网址），前缀 `lzkg`，
**23 个交换字段**（`EXCHANGE_FIELDS`）。

| 用途 | 端点 | 说明 |
|---|---|---|
| **交换（导出）** | `GET /api/export/xml` | 协作数据集，200 篇 / 3.88 MB；**筛选口径与文献页同源**（复用 `_query_lits`，必须传 `all_rows=True` 否则被压到 100 条上限） |
| **视图** | `GET /api/literatures/{lit_id}/xml` | 单篇结构化 XML |
| **交换（回传预检）** | `POST /api/import/xml/preview` | 逐条 diff，**不写主库** |

**「与导入功能联动」怎么落地的**：回传 XML **只做预检**，
逐条报「哪些字段变了」，改动仍走「预检 → 管理员批准 → 入库」的老链路，
与 xlsx 提案制保持同一套审核语义。**不存在「XML 直接改库」的口子。**

**往返闭环实测**：导出 200 篇 → 改 1 条 `review_status` → 回传预检 →
报出 **1 处差异 / 199 条无变化**，主库未动。

**安全**：上传 XML 一律用 `defusedxml`（防 XXE / billion laughs）。
**未装 defusedxml 就明确报错，不静默降级到标准库**——降级等于把 XXE 防护关掉。

### 4. 原文通道的权限：三档可切，默认全开

`config.json` 的 `raw.access`：

| 值 | 行为 |
|---|---|
| `open`（**默认**） | 登录与否都给原文通道 |
| `login` | 需登录 |
| `oa_only` | 只给开放获取条目 |

用户明确选了「**全开：登录与否都给**」。收紧时**改配置不改代码**。

★ **全开之后界面口径必须跟着改**：页脚原来写「机构订阅件不得外传」，
现在改成「**站内提供原文通道，不代表获得对外传播授权；标注为机构订阅/限内部使用的条目，请勿外传**」。
—— 通道和授权是两回事，这句话不能不改（否则就是在撒谎）。

### 5. 本轮踩过的坑

- **`Content-Disposition: inline; filename="中文.pdf"`** → `latin-1` 编码报错 →
  必须 `filename*=UTF-8''`（RFC 5987）
- **图片替换必须在转义之后**：先 `_sanitize_inline` 转义，再做图片替换。
  反过来的话，自己生成的 `<img>` 会被二次转义 → **图全不显示**（不报错，只是空白）
- **`MD_IMG_RE` 要同时认 `https?://` 和 `/media/img/`**：只认前者的话，
  重写后的本地路径匹配不上 → 页面出现字面 `![image](...)`
- **占位标记不能含 HTML 特殊字符**：用 `@@LZKG_IMG:xxx@@` 而不是 `<!-- -->`，
  且要替换**整段** `![alt](url)` 语法（只换 URL 会留下半截源码）
- **`api_raw` 从 `api_v2` import 会循环依赖**（`app.py` 要 import `api_raw`）→
  `require_admin` / `require_login` **下沉到 `auth.py`**，两边各做薄壳转调
- **`from .app import _query_lits` 必须惰性导入**

## 四之七、收藏页的两层检索

> 用户需求：「收藏界面建议也制作一个检索功能」；
> 选定「**两层都要**：先按题名备注筛，再对结果做全文检索」。

工作台「② 我的收藏」原来只有一张平铺的列表（题名 / 备注 / 收藏时间），收藏一多就没法找。
现在有两个输入框：

| 输入框 | 参数 | 做什么 |
|---|---|---|
| **题名/备注** | `t` | 本地快速筛：题名 + 备注里包含这些词（多词 **AND**，忽略大小写） |
| **全文关键词** | `q` | 全文检索：题名 / 摘要 / 关键词 / 正文（走 FTS5，短词自动降级 LIKE） |

**两层是 AND 关系**：先按题名/备注筛，再在**剩下的**收藏里做全文检索。
两个都留空 → 返回全部收藏（与旧行为一致）。

### ★ 最重要的一条：收藏页检索**不得翻出没收藏的文献**

`q` 是**先在全库检索、再与收藏集合取交集**（复用文献页那套 `_match_lit_ids`），
而不是「先取收藏再逐篇搜」。后者慢，前者快，且两者结果一致。

判据专门盯这条：拿一篇**确定没收藏**的文献的标题词去搜，结果里**不许出现它**，
且每一条结果的 `lit_id` 都必须在收藏集合内。

### 返回结构

`GET /api/favorites?t=…&q=…` → `{items, total, matched, filters:{t,q}, mode}`

| 字段 | 说明 |
|---|---|
| `total` | 收藏总数（**未筛选前**） |
| `matched` | 当前匹配条数 |
| `mode` | 全文检索方式：`fts5` / `like`；没检索时为空 |
| `items[].matched` | 命中层级：`title_note` / `full` / `both` / 空 |

每条比原来多给：`year` / `authors` / `venue` / `keywords` / `abstract` / `open_type` / `doc_type` / `snippet`。
—— 光有题名和备注没法定位，检索时要能看见「哪一篇」。

### 前端两处讲究

1. **片段高亮**：后端 FTS5 的 `snippet()` 带 `<mark>` 标记，直接插进 `innerHTML` 会被当标签，
   整体转义又会把高亮一起转义掉。`escMark()` 的做法是**先整体转义、再把转义后的
   `&lt;mark&gt;` 换回 `<mark>`** —— 高亮保住，片段里的 HTML 仍被转义（`tests/test_favsearch.js`
   直接从 `index.html` 提取真实源码执行来验这两条）。
2. **计数口径要分开说**：「收藏共 N 条，当前匹配 M 条」—— N 是总数、M 是命中数，
   别让用户以为收藏被删了。

### ★ 顺带修掉一个**既有 bug**（v2 起就在）

LIKE 降级分支的片段定位写错了：

```sql
-- 错：max(instr(content, ?), 1) - 40
-- 对：max(instr(content, ?) - 40, 1)
```

`instr()` 返回 1 起的偏移；命中位置靠前时（比如正文开头），`max(11, 1) - 40 = -29`，
而 SQLite 的 `substr` **负起点 = 从末尾往回数** → 片段落在**文末的作者简介**，
命中处根本不在片段里。实测：搜「保护」返回的是「硕士研究生/研究方向为旅游规划与开发…」。

这个 bug **不报错**，只是**给错信息**，而且主文献检索页（`/api/search`）同样受害。
判据现在钉死：「LIKE 分支的片段必须含命中词」。

自动回退到上面的查找顺序 —— 而不是拿着一堆「文件不存在」报错。

### ★ 红线：这些是机构订阅件，**绝不能进公开仓库**

原始 PDF / MinerU 解析 JSON / 文献全文 / 图版，**全部是 CNKI 等机构订阅下载的原件**。
所以：

| 出口 | 规则 | 实现 |
|---|---|---|
| **公开仓库（GitHub）** | **禁止** | `.gitignore` 忽略 `程序/data/source/`；`make_github_release.py` 用**白名单式**收集 data，且加了**硬断言**（发现就直接拒绝生成） |
| **对接包** | **禁止** | `build_package.py` 打包后回读校验，发现 `data/source/` 就**拒绝出包** |
| **数据包**（新） | **允许** | `_tools/build_data_package.py` 单独打包，只给组内/校内传 |

| 包 | 内容 | 体积 | 给谁 |
|---|---|---|---|
| `良渚文献目录站_对接包_v3.8.zip` | 程序 + 库（`lzkg.db`，**可检索的全文与解析 JSON 已在库内**） | ~90 MB | 组员：装完就能跑、能检索 |

`01-程序/data/source/` → 程序自动发现（包里的 `config.json` 只保留 `public` 段，
没有机器相关的 `source.root`），**不用改任何配置**。

### 判据

`tests/test_source_data.py`（**35 项**）：副本文件数与体积的**实测真值**、
登记表在位、同步报告留痕且无冲突、配置指向副本、自动发现优先命中副本、

★ **公开仓库与对接包里都没有 `data/source`**、`.gitignore` 与脚本硬断言都在。

### 为什么路径不写死

`config.py` 用「相对程序根目录 + 通配定位」找数据源（`../.. /02*(良渚文化)*/04_专题研究`），
**整个项目目录搬走也能找到**。也可以用环境变量 `LZKG_SOURCE_ROOT` 覆盖。

### 启动脚本的两条硬规矩

1. **`.cmd` 正文必须纯 ASCII + CRLF。** 中文写进 cmd 正文会被 cmd.exe 咬坏后续行，
   表现是「双击闪退」。中文可以出现在**文件名**里，不能出现在正文里。
2. **解释器探测要问它自己的路径**（`sys.executable`）。
   PATH 上的 `python` 可能是 Microsoft Store 的占位桩，根本不是解释器。

## 七、排障

| 症状 | 原因 | 处理 |
|---|---|---|
| 双击闪退 | `.cmd` 被改成非 ASCII/非 CRLF | 用编辑器重新保存为 ANSI + CRLF |
| 提示找不到 Python | 机器上没有 ≥3.10 | 装 Python 3.10+，或放一个便携版到 `runtime\` |
| 页面显示「后端未启动」 | 服务没起来 | 看启动窗口的报错；`python -m lzkg doctor` 自检 |
| 迁移失败 | 找不到 `04_专题研究` | 设 `LZKG_SOURCE_ROOT` 环境变量指向它 |
| 端口被占 | 8771 被别的进程占 | 改 `config.json` 的 `app.port` |
| 搜索搜不到某篇 | 该篇没进 FTS | `python -m lzkg migrate` 重跑（幂等） |
| 图谱一片稀 | 筛选太严 | 最小度数调回 1；上限调大 |

判据一律写成「必须等于某个实测真值」，而不是「不为空」——
**断言「产物合法」不等于断言「产物正确」**。

其中两条专门盯「组员实测报错」的根因，可以单独跑：

```powershell
python tests/test_webdav_live.py      # WebDAV 全链路（本地 mock，不联网）
node   tests/test_wdsafename.js       # 前端文件名兜底（提取 index.html 真实源码执行）
node   tests/test_browsemerge.js      # 浏览记录合并（同上，防「恢复」冲掉本地记录）
```

- `test_webdav_live.py` 起一个本地 mock WebDAV 服务器，**刻意复刻坚果云的两个真实行为**：
  根目录**可读不可写**（PUT 到根 → 404）、**不自动建父目录**。
  于是「MKCOL 建目录 → PUT 上传 → GET 还原」这条成功路径能真跑一遍
  （含中文 UTF-8 往返、重复上传幂等、越权文件名/目录名拒绝、凭据不外泄）。
  SSRF 防护不受影响：测试只在本进程内临时替换 `_assert_public_host`，
  另有判据验证「不替换时私网确实被拒」。
- `test_wdsafename.js` 从 `index.html` 里**提取 `wdSafeName()` 的真实源码**执行（不手抄），
  断言「前端放过的文件名，后端一定不会判『文件名不合法』」，顺带把整页内联脚本编译一遍防语法崩。
- `test_browsemerge.js` 同样提取真实源码，断言「从 Web Dev 恢复」与「导入 JSON」是**合并**语义：
  本地独有的记录不会被远端冲掉、同一篇取更新时间更晚的那份、合并幂等、脏数据（`null` / 缺 id）跳过不崩。

后两个是 node 脚本；本机没有 node 时，主验收会自动跳过，不算失败。
