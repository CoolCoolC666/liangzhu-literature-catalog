## 一、MinerU 解析后端（契约 §2）

### 1.1 为什么自己写协议客户端，而不是 `import mineru`

本机 MinerU 装在 **uv 工具自己的 venv**（`C:\Users\you\AppData\Roaming\uv\tools\mineru`，
Python 3.12.14），而本站后端跑在 **Python 3.13**。两个环境不通用；
把 3.12 的 site-packages 塞进 `sys.path` 也不行（二进制 wheel 在 3.13 上会炸）。

→ `lzkg/mineru_parse.py` 用 **`httpx`** 按官方 V1 协议自己实现（上传 / 提交 / 轮询 / 下载）。
   `requirements.txt` 里**没有** mineru 依赖（我们不 import 它）。

协议（2026-10-29 在本机 mineru 4.0.6 上**实测**过，形状与官方客户端一致）：

```
GET  {base}/v1/health                       健康（探针不带 key）
GET  {base}/v1/usage                        配额（要鉴权）
POST {base}/v1/uploads                      建上传单 → PUT upload_url → POST /v1/uploads/{id}/complete
POST {base}/v1/parse/jobs                   提交（source: local | file_id；output_formats:["zip"]）
GET  {base}/v1/parse/jobs/{job_id}          轮询
GET  {base}/v1/files/{file_id}/content      下载 zip
```

- **本地**：`http://127.0.0.1:8000`（`mineru-api.exe --host 127.0.0.1 --port 8000`），
  走 `source.type="local"` + 绝对路径；★ 本地 API 要带 `--allow-local-source` 才认本地路径。
- **云端**：`https://mineru.net/api`，走 `source.type="file_id"`（先上传再提交）。
- **同一个客户端**，只差 `base_url` 与 `api_key` 两个参数。

### 1.3 `POST /api/mineru/parse`（multipart）

表单字段：`file`（PDF，必填）、`backend`（`local`/`cloud`，默认 local）、`api_key`（仅 cloud）、
`tier`（默认 `standard`）、`pages`（如 `1-5,8`，默认空=全部）。

真实请求 / 响应：

```
POST /api/mineru/parse
file=LIT-000201_原始PDF.pdf, backend=local, tier=standard, pages=1-3
→ 200
{"ok":true,"data":{
  "job_id":"P-20261029-0003",
  "status":"running",
  "backend":"local",
  "file":"LIT-000201_原始PDF.pdf",
  "tier":"standard",
  "note":"解析在后台跑，用 GET /api/mineru/jobs/{job_id} 查进度"}}
```

实现要点：

- **长任务不挂在 HTTP 请求上**：接口只回 `job_id`，解析在**后台线程**里跑，前端轮询。
- 产物落**暂存区** `data/解析暂存/<job_id>/`（`md/`、`json/`、`images/`），**不写源数据目录**。
- **key 只在这一次请求里用完就走**：不落库、不写日志、不回显；
  异常信息一律过 `mineru_parse.scrub()`（先按本次实际用的 key 精确替换，再补 Bearer / JWT / `api_key=` 通用正则）。
- key 优先级：**请求里的 > `config.json` 的 `mineru.parse_server.remote.api_key` > 环境变量 `MINERU_API_KEY` > 匿名**。

## 二、解析产物 → 提案 → 入库（契约 §3）

### 2.1 `POST /api/mineru/submit`

请求：

```json
{"job_id":"P-20261029-0003",
 "lit_id":"LIT-000201",
 "record":{"题名":"…","作者/责任者":"…","文献类型代码":"DOC-AR｜学术论文",
           "出版/发表时间":"2018","语种":"zh","开放类型/使用条件":"公开（知网/维普下载）",
           "著录人":"…","著录日期":"2026-10-29"},
 "images":[{"filename":"…","caption":"…","fig_no":"…","page":3,"obj_type":"…"}]}
```

真实响应：

```json
{"ok":true,"data":{"staging_id":3,"status":"pending","kind":"parsed","target_id":"LIT-000203",
 "note":"已提交，等待管理员审核（批准前不写主库）"}}
```

实现要点：

- `record` 的键是**登记表列名**（与 `/api/registry/columns` 一致），按**列名**映射成库字段
  （复用 `lzkg/registry.py` 的 `by_name`，不按列序）。
- `lit_id` 不给就**现算**下一个六位流水号（库里最大号 +1，并避开已被提案占用的号）。
- **不写主库**：只写 `staging` 一行（`kind='parsed'`、`status='pending'`、`proposer=当前用户`）。
- 提案行同时记 `job_id` / `source_file` / 产物清单 / 字段级 diff。

真实条目：

### 2.3 批准（`POST /api/staging/{id}/approve`，管理员）

真实响应：

```json
{"ok":true,"data":{"id":3,"status":"approved","applied":true,"result":"inserted","lit_id":"LIT-000203",
 "moved":[{"kind":"md","file":"MinerU_markdown_LIT-000203_原始PDF.md","skipped":false},
          {"kind":"json","file":"MinerU_json_LIT-000203_原始PDF.json","skipped":false},
          {"kind":"json","file":"MinerU_json_LIT-000203_原始PDF_structured_content.json","skipped":false},
          {"kind":"json","file":"MinerU_json_LIT-000203_原始PDF_model_output.json","skipped":false}],
 "missing":[],"image_rows":0,"chars":7196,"pages":3,
 "note":"产物已从暂存区搬进源数据目录，文献行已 upsert 进主库"}}
```

搬进源数据目录的落点（沿用现有命名约定）：

| 产物 | 目标目录 | 命名 |
|---|---|---|
| Markdown | `03_文献全文/` | `MinerU_markdown_<LIT-id>_<原文件名>.md` |
| JSON | `02_解析结果/` | `MinerU_json_<LIT-id>_<原文件名>.json` |
| 图片 | `04_文献图像/` | `IMG-<LIT-id>-<3 位序号>.<ext>` |

- 同时 upsert `literatures` 行（登记表字段 + `md_path` 指针 + `parse_status='已解析'`），
  并补写派生列 `md_chars` / `md_pages` / `md_img_refs`；
  写 `import_log`（`kind='parsed'`）。
- **幂等**：重复批准 → `applied:false`「该提案已处理过」；文件已搬过就跳过，
  文献行是 upsert，`import_log` 不会多出一条。实测见 §五。

## 三、MCP（契约 §4）

### 3.1 形态

- **stdio**：`python -m lzkg mcp` → 本地智能体用。
- **HTTP**：`python -m lzkg mcp --http --port 8801` → 独立进程，供本地测试；
  **并且** `python -m lzkg serve` 时把同一个 MCP 应用挂到本站 FastAPI 上，
  公网地址就是 `https://lztp.example.com/mcp`。

### 3.2 六个只读工具（契约 §4.2）

| 工具 | 入参 | 返回 |
|---|---|---|
| `search_literatures` | `query, doc_type, region, topic, year, limit` | 命中列表 + 片段 + `total` |
| `get_literature` | `lit_id` | 完整题录 + 四维标签 + 来源判据 + 开放类型 |
| `list_images` | `lit_id, limit` | 图版清单（文件名/图注/页码/对象类型） |
| `read_markdown` | `lit_id, max_chars` | 正文 Markdown 摘录（默认前 3000 字） |
| `graph_neighbors` | `node_id, depth, limit` | 图谱邻居 + 关系名 |
| `stats_overview` | — | 库规模、分布、复核覆盖率 |

★ **只读**：没有暴露导入 / 审批 / 删除类工具。
★ 每个工具的返回里都带 **`口径`** 字段（这个数是怎么算出来的）。
   例：`search_literatures` → 「关键词走本地 FTS5 全文索引（≤2 字的词自动退回 LIKE 扫描）；
   类型/分区/主题为包含匹配；年份精确相等；total 是筛选后的总数，returned 是本次返回条数。」
★ `stats_overview` 的复核覆盖率**按 `review_status` 状态字段统计**（复核日期非空 ≠ 已复核）。

### 3.3 怎么挂到 FastAPI 上（`app.py` 不在可改清单里）

`MCPServer.streamable_http_app()` 返回的是**普通 Starlette**，它有两个坑：

1. **lifespan**：会话管理器要靠 `mcp_app.router.lifespan_context(mcp_app)` 启动；
   少了这一步，客户端 `initialize` 直接报 `Server returned an error response`。
2. **挂载位置**：挂载点是 `/`（匹配一切路径），必须挂在**路由表末尾**，
   否则会把既有端点全遮住。

→ `mcp_server.attach_to_host_app()` 的做法：**改宿主的 `router.lifespan_context`**，
   在服务启动那一刻（路由表已定稿）做两件事：进入 MCP 应用的 lifespan、把
   `Mount("/", gated)` **append 到路由表末尾**。`python -m lzkg serve` 时调用。

### 3.4 鉴权（§4.3）

HTTP 端点走**本站规则**（`_AuthGate` 中间件，只拦 `/mcp` 路径）：

- 带本站 token（`X-Auth-Token`）且有效 → 放行；
- 带**已验签的** Cloudflare Access 身份 → 放行；
- 本机免登录模式（`auth.enabled=false`）→ 放行；
- 都不满足 → **401** `{"ok":false,"error":"请先登录"}`。

实测（另起一个 `LZKG_AUTH_ENABLED=1` 的服务）：

```
POST http://127.0.0.1:8800/mcp → 401 {"ok": false, "error": "请先登录"}
POST http://127.0.0.1:8800/mcp （带无效 token）→ 401
```

stdio 形态是本机进程，直接读库（本机权限）。

## 四、偏离契约的地方（**逐条显式列出**）

| # | 契约写的 | 我做的 | 为什么 |
|---|---|---|---|
| 1 | §2/§3 没写这几个端点的鉴权 | 五个端点全部 `require_login`（批准仍走既有的 `require_admin`） | 契约 §〇 说「新端点沿用本站规则」；`status` 会回本机路径与端口，公网可读等于送地图 |
| 2 | §2.2 `doclib.indexed_docs: 298` | 报 **`null`** + 「索引条数未读取（不依赖它的内部接口）」 | doclib 没有公开的索引条数接口；**编一个数违反「不许编造」**。形状保留、值不编 |
| 3 | §2.4 `progress: "已处理 12/45 页"` | 写「已处理 0/1 个**文件**」 | MinerU V1 的 `progress` 是**按文件**给的（`completed/total`），没有按页的进度；页数在 `result.pages`（现算） |
| 4 | §3.2 只给了 Markdown 的命名约定 | 图片按现有目录的约定 `IMG-<LIT-id>-<3 位序号>.<ext>` 命名 | 契约没规定图片命名；沿用 `04_文献图像/` 里已有的形状 |
| 5 | §3.2 只说「JSON → 02_解析结果/」 | zip 里有 3 个 json：第一个按约定命名，其余加 `_<原名>` 后缀 | 官方 zip 固定给 `middle_json/structured_content/model_output` 三个；全塞进同一个名字会互相覆盖 |
| 6 | §3.4 批准后「产物搬进源目录 + upsert 文献行」 | **另外**把 `submit` 里的 `images` 元数据 upsert 成 `images` 行 | 契约没提，但那批元数据（caption/fig_no/page/obj_type）只有落成图版行才有意义，否则提交的数据被丢掉。**这是超出契约的一处补充** |
| 7 | §4.1「把 `streamable_http_app` 挂到 FastAPI 上（/mcp）」 | 挂载点是 `/`，内部路由是 `/mcp`；**未匹配到的路径**（如 `/api/nonexistent`）会落到 MCP 应用的 404（原来 FastAPI 返回 `{"detail":"Not Found"}`） | `app.py` 不在可改清单里，只能改宿主 lifespan 挂载；`Mount("/")` 必须在路由表末尾才不会遮住既有端点 |
| 8 | §2.1 key 优先级「配置 > 环境变量 > 匿名」 | 在前面加了一层「**请求里的 >** 配置 > 环境变量」 | 契约 §2.3 与 §三都说「每个成员带自己的云端 token」，且 token 存在浏览器里 → 请求里那份必须优先 |
| 9 | §2.2 `cli.path` 是绝对路径 | 照写（`C:\Users\you\.local\bin\mineru.exe`） | 契约示例就是这样；但 `status` 已加登录锁（见 #1） |

**没偏离但要说明的两点**：

- `streamable_http_app(host=...)` 传的是**公网域名**（`config.json` 的 `public.domain`）：
  传回环地址时 SDK 会**自动开启 DNS 重绑定保护**（allowed_hosts 只有 `127.0.0.1`/`localhost`/`::1`）
  → 公网域名会被直接拒。等价于**没开**那层保护；鉴权由 §3.4 的闸兜住。
- 源数据目录里的写入**只发生在批准时**（`importexport._approve_parsed`）；
  解析阶段一律只写 `data/解析暂存/`。
