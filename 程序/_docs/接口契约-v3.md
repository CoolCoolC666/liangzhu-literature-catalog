## v3.3 · Web Dev（WebDAV）—— 把自己的浏览数据同步到自己的网盘

### 浏览记录存在哪

**存在用户自己的浏览器 localStorage 里**，不上传服务器。
键名固定：`lzkg.browse.v1`（浏览数据）、`lzkg.webdav.v1`（WebDAV 配置）。

```json
{"items":[{"kind":"lit","id":"LIT-000001","title":"…","year":"2018","ts":1690000000}],
 "updated_at":"2026-10-29 15:00:00"}
```

- 上限 500 条，超出丢最旧的；同一篇重复浏览只更新时间
- 换设备看不到 → 这才需要下面的 WebDAV 同步

### `POST /api/webdav/test` · `POST /api/webdav/put` · `POST /api/webdav/get`

**全部要求登录**（未登录 401）。body：

| 端点 | body | 返回 data |
|---|---|---|
| `/webdav/test` | `{url, user, password}` | `{ok,status,message,server}` |
| `/webdav/put` | `{url, user, password, name, content}` | `{ok,status,bytes,target,message}` |
| `/webdav/get` | `{url, user, password, name}` | `{ok,status,content,bytes,message}` |

失败统一 `{"ok":false,"error":"人话说明"}`（HTTP 400）。

### ★ 三条边界（界面与文档里都要写）

1. 账号与密码存在**用户自己的浏览器**里，本站**不保存**任何人的 WebDAV 凭据
2. 但测试/上传/下载时，密码会随请求发给**本站后端**再转发给 WebDAV 服务器
   —— 浏览器直连 WebDAV 会被 **CORS** 挡死，这是 WebDAV 的现实。后端**不落盘、不写日志、不回显**
3. 本站后端**只允许公网地址**：`lzkg/webdav.py` 里有 **SSRF 防护**
   （私网/回环/链路本地/保留地址一律拒绝，不跟随重定向，响应上限 2 MB）

### `GET /api/webdev/status` · `POST /api/webdev/toggle`（总闸）

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /api/webdev/status` | 所有人可读 | `{enabled: bool, note}`；前端据此决定**是否渲染入口** |
| `POST /api/webdev/toggle` | **仅管理员** | body `{enabled: true|false}`，写回 `config.json` 的 `webdev.enabled` |

★ 总闸关掉时：**成员**的入口卡片不渲染，接口一律 **403**；
  **管理员仍看得到入口**（否则关了就没法再打开），页面上有「重新开启」按钮。

### 浏览记录「存本站服务器」（v3.4）—— 零配置的那条同步路

WebDAV 要每人自己开第三方应用、生成应用密码、填四项，对只想「浏览过什么别丢」的人太重。
这条路**什么都不用配**：登录后记录自动落到 `data/record/<身份>/browse.json`。

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /api/browse/server/status` | 需登录 | `{enabled, usable, dir, exists, count, bytes, saved_at, note}`；`dir` 只给**相对路径** |
| `POST /api/browse/server` | 需登录 | body `{items: [...], updated_at?}` → `{count, bytes, saved_at, path, dropped}` |
| `GET /api/browse/server` | 需登录 | `{items, count, exists, saved_at}` —— **只返回调用者自己那份** |
| `POST /api/browse/server/toggle` | **仅管理员** | body `{enabled}`，写回 `config.json` 的 `browse_server.enabled` |

**数据形状**：`items` 每项只保留白名单字段 `{kind, id, title, year, ts}`。
客户端多传的字段（`password`、`token` 之类）**一律丢弃**，不进磁盘（返回值里 `dropped` 计数）。

**隔离与边界**（`lzkg/browserec.py`）：

1. 目录名由**后端**从身份推导：本机免登录管理员 → `admin`；登录用户 → `u<id>_<清洗后用户名>`
   —— 客户端传什么名字都进不去（`../` 无效）
2. **没有「按用户名读别人」的入口**，读接口永远只返回调用者自己那份
3. 单份上限 1 MB；**原子写**（`.tmp` → `os.replace`）；覆盖前把旧版留成 `browse.prev.json`
4. 总闸 `browse_server.enabled=false` 时的行为（三道口子，各有理由）：
   - `POST/GET /api/browse/server` → **403**（读写都停）
   - `GET /api/browse/server/status` → **仍 200**，返回 `{enabled:false}`（前端据此说明「已关闭」，
     不然用户只看到一片 403 不知道发生了什么）
   - `POST /api/browse/server/toggle` → **仍对管理员开放**（否则关了就打不开，与 Web Dev 总闸同理）

**与 WebDAV 的关系：并行，不是替代**。
前端按「谁配了就用谁」选同步目标：配了 WebDAV 走网盘，没配走本站服务器，都没有才「未设置」。
自动同步**只做上行**（记录一变就排一次，节流 2.5 秒 + 单飞）；
双向收敛（下载 → 合并 → 上传）只在**手动「立即同步」**里做。

### ★ 坚果云：文件必须放在**已存在的文件夹**里

坚果云**不允许直接往根目录写文件** —— PUT 到 `https://dav.jianguoyun.com/dav/x.json`
返回 **404**（不是 403/409）。所以配置里有**「存放目录」**字段（默认 `lzkg`），
后端上传前会 **MKCOL 自动建出这个目录**。
测试连接也改为测**最终目标目录**而不是根目录 ——
否则会出现「测试连接通过、上传却 404」的迷惑现象。

★ 文件名兜底：浏览器下载后显示的是**完整路径**（如 `下载NDM\lzkg-browse.json`），
用户很容易直接粘进文件名框 → 前端只取最后一段，不因此报错。

### 说明链接（配置区固定挂着）

- 坚果云：第三方应用授权 WebDAV 开启方法 → `https://help.jianguoyun.com/?p=2064`
- WebDAV 是什么 / 怎么用（知乎）→ `https://zhuanlan.zhihu.com/p/397069064`

★ 坚果云要用「第三方应用管理」里生成的**应用授权密码**，不是账号密码。

## 二、MinerU 解析（后端新增）

### 2.1 事实基础（已实测，**别重新发明**）

| 项 | 值 |
|---|---|
| MinerU 版本 | **4.0.6**（`C:\Users\you\.local\bin\mineru.exe`） |
| ★ **不能 import mineru** | 它装在 **uv 工具自己的 venv**（`%APPDATA%\uv\tools\mineru`，**Python 3.12.14**）里，我们跑 **Python 3.13** → `ModuleNotFoundError`。**不要往 sys.path 里塞那个 site-packages**（3.12 的 wheel 在 3.13 上会炸） |
| → 所以 | **自己用 `httpx`（已装）实现 V1 协议客户端**，协议见下 |
| **本地自托管 API** | `mineru-api.exe --host 127.0.0.1 --port 8000`（V1 协议，**无 key**）；**默认没在跑** |
| **云端 API** | `https://mineru.net/api`（V1 协议，要 key） |
| 本机文档库服务 | `mineru server` → TCP `http://127.0.0.1:15980`（`mineru config show` / `usage` 依赖它） |
| 档位 | `flash` / `basic` / `standard` / `advanced` |

#### V1 协议（照这个实现，别猜路径）

```
健康   GET  {base}/v1/health
       → {"features":{"sources":["local","file_id",...]}}
       ★ sources 含 "local" → 可直接传本地路径，跳过上传

配额   GET  {base}/v1/usage                      （要鉴权）

─── 上传（云端要；本地不用）───
建     POST {base}/v1/uploads
       {"filename","bytes","mime_type":"application/pdf","purpose":"parse","sha256sum"}
       → {"id","upload_url","upload_headers","status","file":{"id"}}
       ★ status=="completed" → 直接拿 file.id，跳过 PUT
传     PUT  {upload_url}   文件字节 + upload_headers
       ★ upload_url 以 "/" 开头 → 拼上 {base}
       ★ **同源**才带 Authorization；**外部预签名地址绝不能带 key**
完成   POST {base}/v1/uploads/{id}/complete    → {"file":{"id"}}
查     GET  {base}/v1/uploads/{id}             （轮询到 completed）

─── 提交与轮询 ───
提交   POST {base}/v1/parse/jobs
       {"files":[{"source":{"type":"file_id","file_id":"…"} | {"type":"local","path":"…"},
                   "page_range":"1-5,8"（可选）}],
        "output_formats":["zip"],          ← 要图片/模型输出用 zip；只要 middle_json 用 ["middle_json"]
        "tier":"standard"（可选）,"ocr_mode":"auto|txt|ocr"（可选）}
       → {"job_id","status"}
轮询   GET  {base}/v1/parse/jobs/{job_id}
       → {"job_id","status","files":[{"output_files":{"zip":{"file_id":"…"}}}]}

─── 下载 ───
       GET  {base}/v1/files/{file_id}/content   → 文件字节
       ★ output_formats=["zip"] 时，zip 里**自包含** md / json / 图片，
         不用逐个下载 —— 建议走这条
```

鉴权头：`Authorization: Bearer <api_key>`。

★ **key 只在这一个请求里用完就走**：不落库、不写日志、不回显；错误信息里必须打码
（参考 `lzkg/ai_providers.py` 的 `_scrub`）。

★ **`mineru parse` CLI 不能带 per-call token**（CLI 把请求委托给本地 doclib 服务，
服务端用它自己的配置）→ per-member 的 token **只能我们自己调 V1 API** 才传得进去。

★ 本地与云端**只差 `base` 与 `key` 两个参数**，用同一份客户端代码。

### 2.2 `GET /api/mineru/status`

探测本机能力（**不含任何密钥**）：

```json
{"ok":true,"data":{
  "cli":   {"installed": true, "version": "4.0.6", "path": "…"},
  "local": {"api_url":"http://127.0.0.1:8000","reachable":true,"tier":"standard",
            "note":"本地自托管 API；用 mineru-api.exe --port 8000 起"},
  "doclib":{"running":true,"tcp":"http://127.0.0.1:15980","indexed_docs":298},
  "cloud": {"api_url":"https://mineru.net/api","reachable":true,
            "note":"云端配额取决于成员自己的 token"},
  "tiers": ["flash","basic","standard","advanced"]
}}
```

- `reachable` 必须是**真的探一下**（本地打 `/health` 或 V1 探针；云端探针**不带 key**，
  因为匿名探针只是为了知道「地址通不通」）
- 探不通就 `reachable:false` + 说明，**不要抛 500**

### 2.3 `POST /api/mineru/parse`（multipart）

表单字段：

| 字段 | 说明 |
|---|---|
| `file` | PDF（必填） |
| `backend` | `local`（默认）或 `cloud` |
| `api_key` | **仅 `backend=cloud` 时需要**；会员自己的 mineru.net token |
| `tier` | `flash`/`basic`/`standard`/`advanced`，默认 `standard` |
| `pages` | 页范围（`1-5,8` / `all`），默认空（全部） |

★ **key 的处置，和 AI 接口完全一样**：
只用这一次请求，**不落库、不写日志、不回显**；错误信息里必须打码。

**同步返回**（解析可能几分钟，所以**必须后台跑 + 轮询**，不要让 HTTP 请求挂着）：

```json
{"ok":true,"data":{
  "job_id":"P-20261029-0001",
  "status":"running",
  "backend":"cloud",
  "file":"xxx.pdf",
  "note":"解析在后台跑，用 GET /api/mineru/jobs/{job_id} 查进度"
}}
```

## 三、解析产物 → 提案 → 入库（协作链路）

### 3.1 参照 msyt 的数据传输原理

msyt 的模型是：**成员的算力/额度在成员那边 → 算完回传权威库 → 管理员审核后合并**
（回传走**合并覆盖**语义 → 幂等 → 可重试）。

我们这边照搬：

```
成员浏览器上传 PDF
   ↓  后端用【成员自己的云端 token】（或本机 API）解析
   ↓  产物落在暂存区
成员填题录信息 → 提交提案
   ↓  进 staging（status=pending，proposer=当前用户）
管理员在「工作台 → 提案与审核」里逐条批准
   ↓  产物从暂存区【搬进源数据目录】，文献行 upsert 进主库
   ↓  写 import_log
```

★ **和 msyt 一样，批准前不动权威库。**
★ **和 msyt 一样，回传/批准是幂等的**——同一份提案重复批准不产生第二份数据。

### 3.2 暂存区

- 路径：`data/解析暂存/<job_id>/`，里面有 `*.md`、`*.json`、图片目录
- **不进源数据目录**（`04_专题研究/`），直到批准
- 批准成功后**移动**到源数据目录的对应位置：
  - Markdown → `03_文献全文/`
  - JSON → `02_解析结果/`
  - 图片 → `04_文献图像/`
- 目录名沿用现有约定：`MinerU_markdown_<LIT-id>_<原文件名>.md`

### 3.3 `POST /api/mineru/submit`

body：

```json
{"job_id":"P-20261029-0001",
 "lit_id":"LIT-000201",
 "record":{"题名":"…","作者/责任者":"…","文献类型代码":"DOC-AR",
           "出版年":"2026","语言":"zh","开放类型":"…","著录人":"…","著录日期":"2026-10-29"},
 "images":[{"filename":"…","caption":"…","fig_no":"…","page":3,"obj_type":"…"}]}
```

- `record` 的键用**登记表列名**（与 `/api/registry/columns` 一致）
- `lit_id` 不给就自动生成（下一个六位流水号）
- 返回 `{"ok":true,"data":{"staging_id":123,"status":"pending","note":"已提交，等待管理员审核"}}`
- **不写主库**

### 3.4 提案的种类（`staging.kind`）

| kind | 含义 | 批准后 |
|---|---|---|
| `literatures` | 改/加一条文献行（v2 已有） | upsert `literatures` |
| `images` | 改/加一条图版行（v2 已有） | upsert `images` |
| `parsed` | **新增**：一份 PDF 的解析产物 + 题录 | 产物搬进源目录 + upsert 文献行 |

### 3.5 提案列表要能看出「这是哪来的」

`GET /api/staging` 的每条要带：`kind`、`target_id`、`proposer`、`created_at`、
`diff`（字段级）、以及 `parsed` 类提案的**产物清单**（md/json/图片数）。

## 四、MCP（后端新增）

### 4.1 形态

用**已安装的 MCP Python SDK 2.x**（★ `FastMCP` 在 2.x 已改名 `MCPServer`）。

**已实测跑通的配方**（照抄，别自己摸索）：

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from mcp.server.mcpserver import MCPServer   # ★ 2.x 没有 FastMCP

mcp = MCPServer(name="lzkg", instructions="…")

@mcp.tool(description="…")
def search_literatures(query: str, limit: int = 10) -> dict:
    """……"""
    return {...}

mcp_app = mcp.streamable_http_app(
    streamable_http_path="/mcp",
    host="lztp.example.com",     # ★★ 见下
)

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with mcp_app.router.lifespan_context(mcp_app):   # ← 是 router.lifespan_context
        yield

app = FastAPI(lifespan=lifespan)
app.mount("/", mcp_app)
```

**五个已踩过的坑**（上面的配方都已规避）：

| 坑 | 说明 |
|---|---|
| `FastMCP` 不存在 | 2.x 改名 `MCPServer`（`from mcp.server.mcpserver import MCPServer`） |
| `mcp_app.lifespan` 属性不存在 | 它是普通 Starlette → 要用 `mcp_app.router.lifespan_context(mcp_app)`。**少了这步，客户端 `initialize` 直接报 "Server returned an error response"** |
| 客户端函数名 | 2.x 是 `streamable_http_client`（1.x 是 `streamablehttp_client`） |
| 客户端 yield 的值个数 | 2.x 是 **2 个**：`as (r, w):`（1.x 是 3 个） |
| ★★ **公网部署要传 `host`** | `host` 是回环地址时**自动开启 DNS 重绑定保护**，`allowed_hosts` 只有 `127.0.0.1:*`/`localhost:*`/`[::1]:*` → **公网域名会被直接拒**。传我们自己的域名即可 |

**形态两选都要**：

- **stdio**：`python -m lzkg mcp` → 本地智能体用
- **HTTP**：把上面的 `mcp_app` 挂到 FastAPI 上 → 公网智能体用
  `https://lztp.example.com/mcp`

**自测写法（client 侧）**：

```python
from mcp.client.streamable_http import streamable_http_client
from mcp.client.session import ClientSession

async with streamable_http_client("http://127.0.0.1:8799/mcp") as (r, w):
    async with ClientSession(r, w) as s:
        await s.initialize()
        tools = await s.list_tools()
        res = await s.call_tool("search_literatures", {"query": "良渚 玉琮", "limit": 3})
        print(res.content[0].text)
```

## 六、已知的坑（别再踩一遍）

| 坑 | 说明 |
|---|---|
| **`FastMCP` 在 MCP 2.x 里不存在** | 改名 `MCPServer`（`from mcp.server.mcpserver import MCPServer`） |
| **`mineru parse` CLI 不能带 per-call token** | CLI 把请求**委托给本地 doclib 服务**（15980），服务端用它自己的配置 → per-member token 传不进去。**必须直接用 `MinerUApiParser(api_url=..., api_key=...)`** |
| 本地 MinerU API 在 **8000**，不是 15980 | 15980 是 doclib（文档库）服务；8000 才是解析 API（`mineru-api.exe --port 8000`） |
| `mineru config show` / `usage` 需要本地服务在跑 | 服务没起会直接报错退出 |
| 源数据目录是**共享**的 | 解析产物在**批准前**只能落在暂存区，不能直接写 `04_专题研究/` |
| 长任务不能挂在 HTTP 请求上 | 解析要几分钟 → 后台任务 + 轮询 |

### `GET /api/stats/mapdata` → 交互地图的点级数据

`{ok:true, data:{site_group, points, regions, sites, counts, notes}}`

| 字段 | 内容 |
|---|---|
| `site_group` | 良渚遗址群范围框（`lon_min/lon_max/lat_min/lat_max`）+ 中心点 + 出处与原文摘录 |
| `points[]` | 4 个**文献坐标点**：`{id,name,lon,lat,kind,source,lit_count,lits[],match_keys[],linked}` |

| `notes[]` | 口径说明字符串数组 |

**关联文献口径**（写死在 `notes` 里，别自己猜）：
- 分区代表点 → 按 `tags.dim='region'` 的名称**精确关联**
- 文献坐标点 / 候选遗址 → 按**题名/摘要/关键词/刊名的文本命中**关联
- ★ 关键词必须精确到那一篇/那一类，**不许回退到「良渚」这种宽泛词** ——
  回退过一次，结果「MFL 高坝剖面点」关联出 120 篇（实际 1 篇），那是**假关联**，比不关联更坏

**前端画图时的硬约束**：
- `on_map=false` 的分区**不许画成有坐标的点**（给主题类/范围类分区配坐标就是编造位置）
- `lat/lon` 为 null 的**不许画**（也不许估一个位置）
- 区域代表点必须标注「示意，±1.1 km，非实测坐标」

## v3.5 · 图谱降密度 + 文献详情内嵌地图标记

### `GET /api/graph` 的两个新参数（默认值即新行为，向后兼容）

| 参数 | 默认 | 说明 |
|---|---|---|
| `edge_cap` | `6` | 边裁剪的**度数上限**：任何节点的度数都不得超过它（孤点接回后最高 `edge_cap×2`） |
| `dense` | `true` | `true` = 做三处降密；`false` = 保留旧行为（全边 + 全图坐标），用于对照 |

**响应新增字段**（既有字段一律不动）：

| 字段 | 位置 | 说明 |
|---|---|---|
| `label_nodes` | 顶层 | 该显示名字的节点 id 列表（按**社区轮转**排序，前 12 个正好每社区一个） |
| `show_label` | 每个节点 | 该节点是否带名字；`false` 的节点名字只在悬停提示里出现 |
| `stats.raw_nodes` / `stats.raw_edges` | stats | 裁剪**前**的节点数 / 边数（口径要写出来） |
| `stats.pruned_isolated` | stats | 剔除的孤点数 |
| `stats.edge_cap` / `stats.dense` | stats | 本次用的上限与是否降密 |

★ `dense=true` 时所有节点的 `x`/`y` 都是**按裁剪后的子图重算**的
（后端算好、seed 固定，前端 `physics:false` → 同一份数据永远画出同一张图）。

★ 前端若要按缩放做**渐进披露**（全图 12 个 → 中等 24 个 → 全部），
**必须另存原始标签**（本项目用 `full_label`）：隐藏时把 `label` 置空后，
再放大时从 `label` 读回来就是空串，标签再也放不出来。
★ vis-network 的 `moveTo({scale})` **不触发** `zoom` 事件 → 需要 scale 轮询兜底。

### `GET /api/literatures/{lit_id}/map` → 这一篇文献的地图标记（新增）

`{ok:true, data:{lit_id, found, title, year, level, level_label, markers[], pending_sites[], site_group{}, notes[]}}`

**四档精度（`markers[].tier`）**：

| tier | `level_label` | 含义 | 精度 |
|---|---|---|---|
| `lit_coord` | 文献坐标 | 坐标由**文献**给出；`from_this_paper=true` 表示**出处就是本篇** | 点级（米级） |
| `public` | 公开权威坐标 | 出处是公开权威资料（如良渚古城遗址整体） | 遗址整体（百米级） |
| `region` | 分区代表点 | 本篇带空间分区标签，落在分区代表点上 | **区块统一坐标，约 ±1.1 km** |
| `none` | 未定位 | 没有可定位坐标 | —— |

`markers[]` 每条带：`{kind, name, lat, lon, tier, tier_label, from_this_paper,
source, source_title, basis, note, precision, why}` —— 
`precision`（精度说明）、`source`（出处）、`why`（命中依据）**三样必填**。

**硬约束**：
- ★ 匹配不到就是「未定位」，**不推测填充**；前端此时小地图**留空并写明原因**。
- ★ 主题类分区（数字化 / 文化创意 / 参考案例 / 跨遗址）**不配点**。
- ★ 坐标一律 WGS84，**不得**用 GCJ02/BD09 冒充。
- ★ 与 `GET /api/stats/mapdata` **共用同一份关键词表**（`POINT_KEYS`，模块级），
  两边的关联口径不会各说各话。
- `pending_sites[]`：正文提到但**坐标待补**的候选遗址（只给名字，不配点）。
