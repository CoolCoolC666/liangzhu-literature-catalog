## 〇、先说结论（给不想读全文的人）

1. **现在能搜，但搜得慢、搜不准**。实测：两字词（「兽面」「遗址群」）走 `LIKE` 全表扫，单次 **19–24 ms**；
   三字以上走 FTS5 trigram，**3–10 ms**。慢的不是"数据多"（全库才 201 篇），是"两字词没法进索引"。
2. **通用分词不能直接用**。`jieba` 会把「神人兽面纹饰」切成 `神人/兽面/纹饰`、
   把「良渚文化遗址群」切成 `良渚文化遗址/群`、把「草鞋山」切成 `草鞋/山`。
   良渚语料里最该被当成整体的东西，恰恰是通用分词最先切碎的。
   → 必须配**良渚领域词典**，且词典是数据文件、不是硬编码。
3. **本机现成的工具已经够用，不用再装检索引擎**：
   `jieba 0.42.1`（MIT，已装）做分词，SQLite 内置的 `FTS5 unicode61` 做词级索引，
   `OpenRefine`（Java 26 已装）做离线词典清洗。**不装** Whoosh / tantivy / Elasticsearch。
4. **方案里有两个反直觉的实测结论**（下面 §3 有完整数据）：
   - **分词模式不是精确模式的超集，反而是子集**——两者语义不同，必须**并存 + 合并**，不能互相替代。
   - **扩召回必须过滤单字**——否则「遗址群」会多捞出 **74 篇全是假阳性**（含原词的 0 篇）。
5. **实施结果**：P0–P5 全部完成，判据 **31 项全绿**（`test_segment.py`）+ 原有 **166 项全绿**（`test_all.py --api`）；收尾全量回归 **359 项全通过**。
   词级索引实测 **201 篇 / 1,835,789 token / 重建 6.1–7.4 秒 / 索引 15.57 MB**。
   依赖：本机已装 `jieba`；若交付环境无 `jieba`，检索自动降级（**不会导致程序起不来**）。

## 一、为什么是现在做

《后续功能设计报告》把「④-b AI 问答（带引用）」排在草稿 4a 检索增强**之后**，理由很实在：

- AI 问答的链路是 `问题 → 检索 top-k 片段 → 送 LLM → 带引用的回答`。
- **检索质量直接决定回答质量上限**。现在送去 LLM 的是「子串匹配到的片段」，
  搜「兽面」给不出「神人兽面纹饰」那一段——因为「兽面纹」被切整了，搜「兽面」反而搜不到它。
- 更关键：**没有引用的答案不上屏**（这是项目一贯纪律）。
  检索层召回不全 → 引用不全 → 回答残缺 → 整条链路白做。

所以 ④a 不是"锦上添花的检索美化"，它是 ④b 的**前置地基**。

## 二、现状：现在到底是怎么搜的

### 2.1 机制（代码实测，不是推测）

| 环节 | 现状 | 出处 |
|---|---|---|
| 索引表 | `docs_fts`（FTS5，`tokenize='trigram'`），201 行 / content 7,462,146 字节 | `lzkg/db.py:242` |
| 分词器 | **trigram** = 字符级三元组，**不是词级** | 同上 |
| 查询分流 | 全部 token 长度 ≥3 → FTS5 `MATCH`；**只要有一个 token <3 → 整条查询退回 `LIKE` 全表扫** | `lzkg/db.py:367` `needs_like()` |
| 命中片段 | `substr(content, max(instr(content, ?) - 40, 1), 130)` | `lzkg/app.py:320` |
| 检索入口 | `GET /api/search?q=&page=&size=&…` → `_query_lits()` → `_match_lit_ids()` | `lzkg/app.py:539` / `289` |

> ⚠ 这里的 `max(instr(...) - 40, 1)` 是 v3.7 修过的（原来写反了，SQLite 的 `substr` 负起点 = 从末尾倒数，
> 命中片段会落在文末作者简介）。**改动检索层时不要把它改回去。**

### 2.2 三个实测痛点（每一项都有数）

**痛点 ①　两字词退化成全表扫**

trigram 要求查询词 ≥3 字符，两字词在 FTS5 里**索引不到**（实测 `MATCH '"玉琮"'` 返回 **0 篇**，
而 `LIKE '%玉琮%'` 返回 **67 篇**）。当前做法是整条查询退回 `LIKE`：

| 查询词 | trigram/LIKE 耗时 | 命中 |
|---|---|---|
| 兽面 | 20.7 ms | 52 篇 |
| 玉琮 | 20.3 ms | 67 篇 |
| 遗址群 | 6.4 ms | 60 篇 |
| 良渚文化（≥3 字，走 FTS5） | 10 ms | 120 篇 |

> ⚠ 上表耗时是 **v0.1 探针值**；**实施期实测** `LIKE` 全表扫 **19.6 ms**（中位）。
> **命中篇数是实施期真值，未变。**

全库才 201 篇、7.4 MB，20 ms 谈不上卡。但**两字词是考古文献里最高频的查询**（兽面、玉琮、刻符、反山、瑶山），
这个路径每次都要走。

**痛点 ②　子串匹配 ≠ 词级匹配，检索结果"看着对但不对"**

实测（`jieba` 默认词典，无领域词典）：

| 输入 | jieba 的切法 |
|---|---|
| 神人兽面纹饰 | 神人 / 兽面 / 纹饰 |
| 良渚文化遗址群 | 良渚文化遗址 / 群 |
| 草鞋山 | 草鞋 / 山 |
| 玉琮玉璧玉钺 | 玉琮 / 玉璧 / 玉钺 ✅ |

「草鞋山」是**新石器时代遗址名**，「良渚文化遗址群」是**正式称谓**——
被切开后，它们在词级索引里就散架了。而按整串搜，它们又恰好命中（trigram 是子串匹配）。
→ **两种语义各有各的用武之地，谁也替代不了谁。**

**痛点 ③　通用分词切碎固定词组（量化）**

对 203 篇 MD（合计 **1,637,375 个汉字**）做 n-gram 统计：

| 固定词组 | 出现次数 | 通用分词下的碎片 |
|---|---|---|
| 良渚文化 | 5,410 | 良渚文（5,666）+ 渚文化（5,415） |
| 良渚古城 | 1,586 | 渚古城（1,587） |
| 良渚遗址 | 1,111 | 良渚古（1,661） |
| 神人兽面 | 595 | 神人（904）+ 兽面（1,176） |
| 刻符 | 109 | （这个恰好不切碎） |

> 「良渚文」「渚文化」这类碎片词**根本不是词**，却比「良渚文化」本身还多——
> 这是子串切分统计的必然结果：**真词的 n-gram 碎片必然比真词更"多"**。
> 所以一旦用碎片去建索引，索引里塞的就是垃圾。

**痛点 ④　同义/近义表达召不回**

用户搜「良渚文化」，语料里写「良渚文化」「良渚遗址」「良渚文化遗址群」「良渚古城」的都有。
现在只能靠用户自己一个个试。实测：词级 + 同义扩展后，「良渚文化」能召回 **130 篇**，
比 trigram 的 120 篇**多 11 篇真扩展**（这 11 篇含原词，只是写法不同）。

## 三、两个反直觉的实测结论（方案的地基）

> 这一节是本方案最值钱的部分。**下面每一条都是跑出来的，不是推演出来的。**
> 写方案时我原本以为"分词模式 = 精确模式的超集"，实测推翻了。

### 3.1 分词模式是精确模式的**子集**，不是超集

做法：在内存里建一张 `FTS5(tokenize='unicode61')` 词级索引，
正文经 jieba 分词后用**空格连接**（让 unicode61 把每个词当独立 token），
对照现有 trigram 索引，**16 个查询词**逐个比命中集合：

| 查询 | trigram 命中 | 词级命中 | 关系 | 词级多召回 |
|---|---|---|---|---|
| 玉琮 | 67 篇 | 67 篇 | = | 0 |
| 反山 | 69 篇 | 69 篇 | = | 0 |
| 瑶山 | 66 篇 | 66 篇 | = | 0 |
| 刻符 | 14 篇 | 14 篇 | = | 0 |
| 聚落 | 63 篇 | 63 篇 | = | 0 |
| 墓葬 | 88 篇 | 88 篇 | = | 0 |
| 莫角山 | 50 篇 | 50 篇 | = | 0 |
| 广富林 | 20 篇 | 20 篇 | = | 0 |
| 河姆渡 | 25 篇 | 25 篇 | = | 0 |
| 石家河 | 16 篇 | 16 篇 | = | 0 |
| 兽面 | 52 篇 | 27 篇 | ⊂ | 0 |
| 神人 | 46 篇 | 43 篇 | ⊂ | 0 |
| 良渚文化 | 120 篇 | 119 篇 | ⊂ | 0 |
| 良渚古城 | 77 篇 | 77 篇 | = | 0 |
| 遗址群 | 60 篇 | 38 篇 | ⊂ | 0 |
| 水坝 | 29 篇 | 28 篇 | ⊂ | 0 |
| **合计** | | | | **多召回 0 篇** |

**根因**：整切的领域词会变成**更长的 token**，于是搜它的**子串**就搜不到了。
例：词典里有「兽面纹」，正文里的「兽面纹」整切成一个 token；
再搜「兽面」→ 匹配不上「兽面纹」这个 token → 少 25 篇。
同理「良渚遗址群」整切后，搜「遗址群」也匹配不上。

**所以**：trigram 语义 = **子串匹配**（"兽面"命中"兽面纹"里的兽面）；
词级语义 = **词匹配**（"兽面"只命中独立的"兽面"）。
**两者语义不同，不是同一件事的新旧版本。**

**落地口径**：
- 界面提供三个选项：**整句精确**（A）/ **分词扩召回**（B）/ **两者合并**（A ∪ B，默认）。
- 合并口径实测（6 个查询词）：并集命中数 **恰好等于** trigram，**0 篇假阳性、0 篇漏**。
- 结果条目标注命中层级：`子串命中` / `词级命中` / `同义命中`。
- 计数写清口径：`共 N 篇（子串 X · 词级 Y · 同义 Z）`，不写含混的"共 N 篇"。

### 3.2 扩召回**必须过滤单字 token**

上一轮实测里，「遗址群」词级 OR 模式命中 **133 篇**，比 trigram 的 60 篇多 74 篇。
看着像"扩召回成功了"，其实是**假阳性**：

```
「遗址群」 切词 = 遗址 / 群
  OR 多出的 74 篇里，含原词「遗址群」的 → 0 篇
  单字「群」单独命中 56 篇（"新石器时代晚期文化遗址群"、"…良渚遗址群范围内"…）
  单字「山」单独命中 70 篇（"辽河流域的红山文化"、"杭州市余杭区良渚古城姜家山墓地"）
  单字「城」单独命中 33 篇　　单字「玉」单独命中 63 篇
```

**规则**：扩展检索时，**长度 < 2 的 token 一律丢弃**；若丢弃后无 token 可用，退回原词整体匹配。
过滤后「遗址群」假阳性归 **0 篇**。

### 3.3 分词模式的**真增益是速度**

| 查询 | 现在（LIKE / trigram） | 词级索引 | 提升 |
|---|---|---|---|
| 兽面 | 20.7 ms | 0.54 ms | **38×** |
| 玉琮 | 20.3 ms | 0.81 ms | **25×** |
| 遗址群 | 6.4 ms | 0.49 ms | **13×** |

**这就是词级索引最实在的价值**：把"两字词必须全表扫"这个绕路消掉。

> ⚠ 上表是 **v0.1 探针的估算**（内存态索引、单次计时）。
> **实施期实测**（真库、真 HTTP、预热后取中位）：`LIKE` 全表扫 **19.6 ms** vs
> 词级命中集 **1.31–5.78 ms** → **3.4×**（不是 38×）。
> 差距来自两点：① 探针没算上 FTS5 posting list 的实际长度差异；
> ② 实施期判据测的是**完整命中集**（含 posting list 遍历），不是单次 MATCH 调用。
> **3.4× 才是能写进交付物的数**，38× 只说明"方向对"。

### 3.4 新词发现：直接抄 cacx 会翻车，两处必须改

cacx（网信办作业）的「分词实验室」用凝固度 + 邻字熵挖新词，这套算法直接搬过来**在良渚语料上不好使**，
实测了两处坑：

**坑 ①　候选被短语碎片淹没**

| `min_count` | 候选数（v0.1 探针） | 候选数（**实施期实测**） | Top5 |
|---|---|---|---|
| 5 | 18,685 | — | 良渚考古遗址(5) / 良渚主题(5) / 区域的遗址(6) / 兴隆洼文化(6) / 传递文化(6) |
| 10 | 7,334 | — | 良渚瓶窑一带(10) / 公共文化(10) / 芦城孜类型(10) / 良渚文化末期(10) / 反映遗址(10) |
| 20 | 2,641 | **4,260** | 汇观山祭坛(21) / 石峡遗址(22) / 反山王陵(28) / 凌家滩文化(23) / 当时社会(23) |
| 30 | 1,475 | **2,407** | 人类社会(38) / 社会文化(35) / 中初鸣遗址群(31) / 良渚文化元素(34) / 科技考古(36) |

> ⚠ **实施期候选数比 v0.1 探针多**（min_count=20：2,641 → **4,260**）。
> 原因：v0.1 探针跑在**旧词典**上（那时领域后缀表还没定稿），
> 闸门 ⑥ 领域加权把一部分候选顶掉了；实施期用的是最终词典。
> ★ **Top5 两边一致** —— 说明算法行为一致，差别在词典，不在算法。
> 接口默认 `topn=300`（一次最多返回 300 个候选，够人工勾选了）。

`min_count=5` 时**所有候选的凝固度完全相同（12.69）**——凝固度是频次的函数，
频次相同则分数相同 → **分数根本没有区分度**。必须 `min_count ≥ 20`。

**坑 ②　没有领域加权，Top10 全是垃圾**

| 排序 | Top10 |
|---|---|
| 无领域加权 | 古城园区 / 旅游资源 / **小糊涂仙** / 随葬品数量 / 技术应用 / 汇观山祭坛 / 等级划分 / 进行系统 / **可以根据** / 数字化技术 |
| **加领域加权** | 汇观山祭坛 / 石峡遗址 / 反山王陵 / 凌家滩文化 / 当时社会 / 人类社会 / 河姆渡遗址 / 良渚文化聚落 / 遗址博物馆 / 莫角山台地 |

领域加权 = 命中领域后缀/前缀（遗址 / 古城 / 文化 / 聚落 / 墓地 / 玉琮 …）就 **+3.0 分**。
这一改，Top10 从"半垃圾"变成"全是真领域词"。

**坑 ③　「可切分就淘汰」这条规则会误杀真词**

cacx 的规则：候选能切成两个已知词 → 是短语，淘汰。
在良渚语料上，`遗址群` = `遗址`(在领域词典) + `群`(单字在通用词典) → **被误杀**。
而「遗址群」在语料里出现 **827 次**，是最高频的领域复合词之一。

**修正**：可切分检查要求**两侧都是多字词**（长度 ≥2）才算"可切"。
修正后「遗址群」确实进了候选——但排在**第 4001 位**（因为它频次太高，凝固度分母也高）。

**实施期量化对照**（同一份语料、同一组参数，全量跑一遍新旧两版规则）：

| 规则 | 候选数 | Top5 |
|---|---|---|
| **新规则**（两侧 ≥2 字）+ 领域加权 | **4,260** | 汇观山祭坛 / 石峡遗址 / 反山王陵 / 凌家滩文化 / 河姆渡遗址（**全是真领域词**） |
| 新规则 + **不加权** | 4,258 | 古城园区 / 旅游资源 / 小糊涂仙 / 随葬品数量 / 技术应用（**全是垃圾**） |
| 旧规则（可切就淘汰）+ 加权 | **4,084** | 同上（真领域词） |
| 旧规则 + 不加权 | 4,082 | 同上（垃圾） |

两个可复现的结论：

1. ★ **旧规则比新规则少 176 个候选**（4,084 vs 4,260）—— 这 176 个是被误杀的真领域复合词
   （「遗址群」是其中之一）。**修正不是"更宽松一点"，是修回被扔掉的真词。**
2. ★ **领域加权只改排序、不改候选数**（4,260 vs 4,258，差 2）——
   加权不是"多捞词"，是"把真领域词顶上来"。所以 Top5 从垃圾变成真词，
   而候选总数基本不动。**汇报时不能说加权扩大了候选池**（实测不支持）。

**坑 ④　排序不能只有"得分"一个通道**

「遗址群」频次 827 却排第 4001 → **高频领域复合词被埋**。
→ 候选榜必须给**三个排序通道**：`按得分` / `按频次` / `按邻字熵`，
并配一个**可编辑的领域后缀表**（用户自己维护），让排序规则不写死在代码里。

## 四、技术方案

### 4.1 分层结构

```
用户查询
   │
   ├─ ① 精确层（模式 A）── 现有 trigram 索引，一字不改
   │      语义 = 子串匹配；≥3 字走 FTS5，2 字走 LIKE
   │
   ├─ ② 词级层（模式 B）── 新增 FTS5 unicode61 词级索引
   │      语义 = 词匹配；由 jieba + 领域词典分词，空格连接后入索引
   │
   ├─ ③ 扩展层 ── 领域词典的同义/近义组
   │      如 良渚文化 ≡ 良渚遗址 ≡ 良渚文化遗址群 ≡ 良渚古城
   │
   └─ 合并口径：A ∪ B ∪ C，每条结果标注命中层级
```

**关键约束：不动 `docs_fts`。**
trigram 索引是「能精确复现历史检索结果」的基线，新索引另建一张表，
出问题可以一键关掉新层、退回现状（配置开关）。

### 4.4 词级索引（新增表，不动 `docs_fts`）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS docs_seg USING fts5(
  title, body, lit_id UNINDEXED, tokenize='unicode61'
);
-- body = 分词后用空格连接的文本；title 同理
-- lit_id 用 UNINDEXED（与 docs_fts 保持一致，只存不算索引）

CREATE TABLE IF NOT EXISTS segment_meta (
  segment_version INTEGER PRIMARY KEY,   -- 分词/词典版本号
  dict_hash      TEXT NOT NULL,          -- 领域词典文件的 sha256
  built_at       TEXT NOT NULL,
  doc_count      INTEGER NOT NULL,
  token_count    INTEGER NOT NULL,
  note           TEXT
);
```

**为什么用 `unicode61` 而不是 `trigram`**：
`trigram` 是字符三元组（子串语义），`unicode61` 是词（按分隔符切的 token）。
我们要的正是"词级"，所以正文必须**先分词再空格连接**，让 unicode61 把每个词当独立 token。

**实测成本**（201 篇，实施期真值）：

| 项 | 实测 | v0.1 探针估算 | 差异说明 |
|---|---|---|---|
| 分词 + 写索引 | **6.1–7.4 s** | 8.0 s | 修掉词典缓存 bug 后反而更快（见下） |
| 索引体积 | **15.57 MB** | ≈15.7 MB | 基本吻合 |
| 全库 token 量 | **1,835,789** | 621,944 | **差 3 倍** —— v0.1 探针只统计了去重词型，与实际 token 位数不是一回事 |
| 去重词型 | **83,796** | 39,008 | 同上 |
| `docs_seg` 行数 | **201** | 201 | 与 `docs_fts` 行数一致 |

> ⚠ **token 量从 62 万变成 184 万，是口径修正不是性能退化**：
> 62 万是探针里「去重词型」那一档的数，184 万是**索引里 token 的总位数**（含重复）。
> 两者不是一回事。v0.1 的附录 B 把它们混在一张表里，本次实施已拆开。

> ★ **实施期修掉的一个性能坑（12 倍）**：`load_dict()` 原来每次分词前都读一遍
> JSON 磁盘并重算哈希 → 201 篇 ≈ 10 万次读盘 → 重建索引 **74.8 s**。
> 改成**按 mtime 缓存**后重建降到 **6.1 s**。这条写进判据注释，防止回退。

**6 秒意味着**：词典改一次 → 重建索引 6 秒 → **"立即生效"做得到**
（前端按钮点下去同步跑，按钮禁用并显示"重建中…（约 6 秒，201 篇）"）。

### 4.5 四档检索模式与合并口径

界面（检索框右侧一个分段控件）：

```
[ 整句精确 ] [ 分词扩召回 ] [ 两者合并（默认） ]
```

**API 层是四档**（界面三选项 → API 四档的映射）：

| API `mode` | 界面选项 | 走哪套索引 | 语义 | 典型用途 |
|---|---|---|---|---|
| `exact` | 整句精确 | `docs_fts`（trigram，不改） | 子串 | 找原文里逐字出现的片段 |
| `word` | —（内部档） | `docs_seg`（unicode61 词级） | 词，**不含同义** | 验证词级层的纯效果 |
| `syn` | 分词扩召回 | `docs_seg` + 同义组 | 词 + 同义组 | 「良渚文化」召回写成「良渚遗址」的 |
| `both` | 两者合并（默认） | `exact ∪ syn` | 两种语义 | 默认 |

> ★ **为什么要拆出 `word`（不含同义）这一档**：
> 加了同义扩展之后，词级层**不再**是精确层的子集了
> （实测「良渚古城」：精确 77 篇，同义扩展后并集 **129 篇**）。
> 不把「纯词级」单独拆出来，就没法回答"同义扩展到底带来了什么"。

**每条结果标注命中层级**：`子串命中` / `词级命中` / `同义命中`（可多标）。
计数口径写在结果区：`共 N 篇（子串 X · 词级 Y · 同义 Z）`。

**同义扩展的实测净增益**（实施期真值，`mode=both`）：

| 查询 | 精确层 | 词级层 | 同义层 | 并集 | 同义净增益 |
|---|---|---|---|---|---|
| 良渚文化 | 120 | 120 | 93 | **129** | **+9** |
| 良渚古城 | 77 | 77 | 129 | **129** | **+52** |
| 遗址群 | 60 | 38 | 129 | **132** | **+72** |
| 兽面 | 52 | 27 | 0 | 52 | 0（无同义组） |
| 玉琮 | 67 | 67 | 0 | 67 | 0 |
| 神人兽面 | 39 | 27 | 0 | 39 | 0 |
| 河姆渡 | 25 | 25 | 0 | 25 | 0 |

> 「遗址群」净增益 **+72 篇** —— 这是同义组（良渚文化组 4 个成员）带来的**真扩展**：
> 这些篇目写的是「良渚文化遗址群」而不是「遗址群」，精确层按「遗址群」逐字找是找不到的。
> **这正是同义扩展存在的意义**：不是把两个语义合并，而是补上"用户想的词"与"作者写的词"之间的差。

**扩展层（模式 B 内部）规则**：
1. 查询先经 jieba + 领域词典切词；
2. **长度 < 2 的 token 丢弃**（§3.2 的硬规则）；
3. 多 token 用 `OR`（扩召回的本意）；若过滤后只剩 1 个 token，退化为该 token 精确匹配；
4. 命中同义组内任一词 → 整组都算命中（同义命中）；
5. **同义组必须由人维护**（在词典文件里），**系统不自动生成同义**——自动同义 = 自动编造。

**片段按页生成**：不对全部命中算片段，只给当页那 20 条算。
实测「良渚文化」全部命中算片段要 **118 ms**，按页生成只要 **29.9 ms**。

### 4.6 新词发现实验室（人工确认才进词典）

抄 cacx 的「分词实验室」范式，但按 §3.4 的实测修正：

**算法**（凝固度 + 邻字熵）：

```
凝固度 cohesion = log( P(ww) / (P(w)·P(w')) )
邻字熵  H(左邻字分布) , H(右邻字分布)
得分    score = cohesion + 0.6 × min(左熵, 右熵) + 领域加权(命中则 +3.0)
```

**六道闸门**（按执行顺序，每道都对应一个实测教训）：

| 闸门 | 规则 | 对应教训 |
|---|---|---|
| ① 频次 | `min_count ≥ 20` | §3.4 坑 ①：count=5 时凝固度无区分度 |
| ② 虚字 | 首尾是「的了和与及或在为是把被就都也很更最又而且但是所以因为这那之其以于从对为」的**一律不收** | 碎片被切在词中间 |
| ③ 熟词 | 已在领域词典或通用词典里的**不收** | 不让用户把已有的东西再采纳一遍 |
| ④ 可切分 | 两侧**都是多字词**且都在词典里 → 淘汰 | §3.4 坑 ③：误杀「遗址群」 |
| ⑤ 邻字熵 | `min(左熵, 右熵) ≥ 0.6` | 邻字熵=0 的串只在一个固定上下文里出现过，是碎片 |
| ⑥ 领域加权 | 命中 `domain_tails/heads` → +3.0 | §3.4 坑 ②：没有加权 Top10 半垃圾 |

**排序三个通道**：`按得分` / `按频次` / `按邻字熵`（§3.4 坑 ④：「遗址群」频次 827 却排 4001）。

**界面上必须写明**（cacx 的同款纪律）：
> ⚠ **候选是候选，不是结论。** 统计方法只能保证"大概率是个词"，
> 保证不了"在这个领域里该收"。收不收由人决定。

**采纳流程**（**全部在管理员可视化前端里完成**，不再要求手改 JSON）：

```
人工勾选候选 → 点「采纳勾选的」 → 写进领域词典（+segment_version）
→ 点「保存词典」 → 点「重建词级索引」 → 立即生效
```

- 采纳接口**只接受明确列出来的词**，不接受"全收"这种含糊指令（一次最多 200 个）。
- 采纳前查重：已在词典里的词进 `skipped` 列表，不重复写入。
- 每次写入先备份 `.bak`。

**OpenRefine 在这一步的用法**（离线，人用）：
把候选导出成 CSV → 丢进 OpenRefine → 用 GREL 表达式 + 聚类做归并（如「石峡遗址」「凌家滩文化」
这类"X 遗址/X 文化"可批量归一）→ 人工确认 → 导出 CSV → 回填进 `lzkg_domain.json`。
**站点不调用 OpenRefine。**

### 4.7 版本纪律：`segment_version`

索引是**派生物**，词典是**源数据**。任何时候都必须能回答"这个索引是用哪版词典建的"。

- `segment_meta` 记 `segment_version` + `dict_hash` + `built_at`。
- 词典改动 → `segment_version + 1` → 重建索引 → 写新记录。
- 查询接口返回 `segment_version`，界面显示"索引版本 v3（词典 2026-10-31 15:20 更新）"。
- **重启后仍在**：词典是磁盘上的 JSON，索引重建信息也在 `segment_meta` 里，不依赖进程内存。
- 改词典但**没重建索引** → 界面必须提示"词典已改，索引待重建"，不能装作已生效。

### 4.8 管理员词典可视化编辑器（本轮新增要求）

> **拍板原话**：「不过词典编辑的话，建议给管理员一个可视化前端」。
> v0.1 方案稿只写了"同义组只放 JSON"——**这一条不够**：让管理员改 JSON 意味着
> 改错一个逗号就可能把整个词典搞坏，而且改完还得知道怎么重建索引。
> → **词典编辑必须给管理员可视化前端**，JSON 只是它的存储格式。

#### 4.8.1 位置与形态

- 工作台独立页签：**⑩ 分词实验室与词典**（`#/work/segment`）。
- 界面分四块：
  1. **① 领域词条**（分组展示，组内可改词/分组/说明，可删，可加）
  2. **② 同义组**（组名 + 成员逗号分隔 + 说明，可删，可加）
  3. **③ 领域后缀 / 前缀表**（逗号分隔的一行文本框，作用于新词发现的领域加权）
  4. **④ 候选新词**（人工勾选才进词典）
- 顶部固定四个动作：**保存词典 / 重建词级索引 / 放弃改动重新读取 / 恢复内置初始词典**。
- 顶部常驻一行**索引状态**（版本 / 词数 / 同义组数 / 覆盖篇数 / 是否待重建），**现取现画**。

#### 4.8.2 权限：两道锁

| 层 | 做法 | 效果 |
|---|---|---|
| **界面层** | 非管理员整张卡**不渲染**（`isAdmin()` 判断），只显示一句"仅管理员可见" | 看不见入口 |
| **接口层** | 全部管理端点 `require_admin` | 手工构造请求也只得到 **403** |

> 只藏界面等于没锁 —— 改个 URL 就能调。管理端点清单：
> `GET /api/segment/dict`、`POST /api/segment/dict`、`POST /api/segment/reset`、
> `POST /api/segment/reindex`、`POST /api/segment/newwords`、`POST /api/segment/adopt`。
> （`GET /api/segment/status` **谁都能读** —— 检索页要显示索引版本。）
>
> ★ 顺带踩过的坑：自定义 `ApiError` 会走 FastAPI 默认的 `{"detail":...}` 信封，
> 与项目契约 §0 的 `{"ok":false,"error":"..."}` 不符 → **必须复用 `api_v2.ApiError`**。

#### 4.8.3 关键交互：词典改了 ≠ 生效了

界面把这条链路写死成三步，并在每步给出明确反馈：

```
① 在下面改词典  →  ② 「保存词典」  →  ③ 「重建索引」  →  才生效
```

- 保存后立刻提示"**索引需要重建才会生效**"，同时状态行变成红色"词典已改、索引待重建"。
- 检索页（所有人可见）同步显示"⚠ 词典已改但索引还没重建"——**不能只让管理员知道**。
- 「恢复内置初始词典」会**先把当前词典存一份 `.bak`** 再覆盖，管理员手滑能救回来。

#### 4.8.4 实施期修掉的三个真 bug（都是这页做出来的）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 点一次「保存词典」，**后缀/前缀表被清空**，新词候选榜 Top10 全变垃圾词 | 首屏渲染时词典还没异步读回来，输入框是空的；保存时把空值写回词典 | `paintSegmentDict()` 里**回填**输入框，且只在值为空时才填 |
| 2 | 词条数/同义组数一直显示「**? 条**」 | 词典异步加载后只重画了表格，标题计数没更新 | 计数拆成独立元素，数据到位后回填 |
| 3 | 保存/重建后状态行**不刷新** | 调了 `loadSegmentStatus()` 但没重画 | 改成 `loadSegmentStatus().then(paintSegmentStatus)` |

> 第 1 条值得记：**「保存」这个动作会把界面上没显示出来的值写回存储**。
> 任何异步加载 + 表单回填的组合，都要防这一手。

#### 4.8.5 验收（浏览器实测，非 headless）

已在真实浏览器里跑通全链路：
添加词条 → 保存（提示"索引需要重建"）→ 状态行转红 → 重建（201 篇 / 1,835,789 token / 7.36 秒）
→ 候选发现（Top12 全是真领域词）→ 采纳 → 恢复默认 → 保存 → 重建。

## 七、风险与边界

| 风险 | 表现 | 应对 |
|---|---|---|
| **分词词数被低估** | jieba 切碎后，词级召回 < 精确召回（**实测确实如此**，兽面 27 vs 52） | 默认用"两者合并"；界面永远能看到两种口径；**绝不用词级替换精确模式** |
| **扩召回引入假阳性** | 实测 74 篇 | 过滤单字 token（硬规则）+ 合并口径要求每条命中含原词或同义词（判据 5） |
| **同义组变成"人工编造"** | 管理员随手加同义 → 召回一堆无关文献 | 同义组必须写 `note` 说明依据；界面显示每组的成员；**同义组改动留痕**（写进 `lzkg_domain.json` 的 git 历史） |
| **索引与词典漂移** | 改了词典没重建索引，界面显示的却像是新的 | `segment_version` + `dict_hash`（§4.7）；界面显示索引版本与词典更新时间 |
| **jieba 加载拖慢启动** | 首次 `jieba.initialize()` 约 0.5–3 s | **惰性加载**：第一次真要用分词时才初始化；启动不等待 |
| **交付包变大** | jieba wheel ≈ 19 MB（对接包现 90 MB） | ① jieba 列为可选依赖，不装也能跑；② 打包脚本提供 `--with-jieba` 开关，默认不带 |
| **新词发现把垃圾收进词典** | 候选误采纳 | 三道人工闸门 + 采纳记录留痕；采纳后可一键回滚（词典是 git 管理的 JSON） |
| **AI 问答抢跑** | 在检索层不稳时先上 RAG | §1 已定：④a 是 ④b 的前置，顺序不换 |

**边界（做什么、不做什么）**：

- ✅ 做：分词、领域词典、双模式、同义扩展、新词发现、索引版本化。
- ❌ **不做**：向量检索 / embedding（需要模型与向量库，本项目明确不做模型旁路 B4）；
  ❌ **不做**：自动同义词生成（自动 = 编造）；
  ❌ **不做**：自动入词典（候选是候选）；
  ❌ **不做**：替换现有 trigram 索引（它是可复现历史结果的基线）；
  ❌ **不做**：中文分词之外的语种增强（本语料是中文考古文献）。
