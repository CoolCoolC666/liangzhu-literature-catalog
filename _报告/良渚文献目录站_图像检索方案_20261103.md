# 良渚文献目录站 · 图像检索方案（E2 / ④c）

> 版本：**v1.1（已实施）**　｜　日期：2026-11-03　｜　对应《后续功能设计报告》草稿 ④c
>
> ★ **v1.1 = 实施后回填实测真值**：§〇-3、§4.2、§十 的数字全部换成实施期实测值，
> 并新增 §十一「实施结果」。**v1.0 里的 38.4% 已被实测推翻**（见 §十一）。
>
> 一句话：把 **3162 张图版**从「详情页的附属物」变成「**可检索对象**」——
> 先做**文字找图**（零新依赖、当天可落地），再谈**以图搜图**（向量层**可选、默认关闭**）。
>
> ★ **定位：图像检索是一个独立模块（E2），与文献检索「并列」而不是「嵌进去」。**
> 独立目录、独立索引表、独立端点前缀、独立前端入口、独立 CLI、独立判据文件，
> 两边只通过 `lit_id` 弱耦合（可互相跳转），**不共用查询逻辑、不共用索引**
> —— 检索是全站最容易长歪的地方，一旦和文献检索共用一套，以后改一边就会弄坏另一边。
>
> 本文所有数字都是**本机实测**（2026-11-03，库 `data/lzkg.db` / 磁盘 `data/source/04_文献图像`），
> 不是估算。实施后如有出入以实施期实测为准，并回来改本文。

## 〇、先说结论（给不想读全文的人）

1. **「图像检索」其实是三件事**，混着谈必然做歪：
   **① 文字找图**（搜"玉琮"→ 返回图版）、**② 以图搜图**（上传一张图 → 找相似图版）、
   **③ 图版找文献**（图版所在文献的全文检索）。
   **只有 ① 和 ③ 能靠现有数据做扎实；② 要向量模型，是另一件事的成本量级。**
2. **现状：图版数据其实很完整，但完全没被检索。** 库里有 **3162 行图版 / 174 篇文献**，
   图注（caption）**100% 有值**、图号/页码/AI 描述/标签**全都齐**，
   `img_tags` 倒排 **21117 行**——但**没有任何图版索引**，检索页只查文献全文。
   → **第一步不是上模型，是把已有的 3162 条文本变成可检索的。**
3. **图注是「中英混排 + 全角字符」**，例如
   `图１ 良渚古城遗址空间数据形态示意图；Ｆｉｇ．１ Ｄｉａｇｒａｍ ｏｆ ｔｈｅ ｓｐａｔｉａｌ ｄａｔａ ｏｆ ｌｉａｎｇｚｈｕ ａｎｄ…`
   → **实施后实测**：做 NFKC 全角归一 + 中英分列后，中文图题解析出 **2168 / 3162（68.6%）**、
   英文图题 **1047（33.1%）**。**清洗规则是这一步的主要工作量，不是模型**（这一点方案写对了）。
4. **AI 描述不能当检索主力**：`ai_desc` 虽 100% 有值，但 **273 条（8.6%）**是
   「图像为示意图，主要展示…；具体视觉细节以原图为准」这种**模板兜底句**，
   `ai_objects` 普遍粗到只有「数据；分析结果」这种两三个词。
   → **AI 描述要做「质量标记 + 降权」，不能当图注用。**
5. **图版复核覆盖率只有 19.6%**（人工核实 405 + 通过 214 = 619 / 3162），
   待复核 2516 条（79.7%）、非文献图像 27 条。
   → **检索结果必须显示复核状态徽标**，否则等于把未核实的判断当结论卖。
6. **向量层（以图搜图）先做成「可选、默认关闭」**：本机 CLIP 权重 + onnxruntime
   会让包体从 120 MB 涨到 500 MB 以上，且与「零外链 / 本机可跑」冲突。
   → **E2-0 落地前不碰模型**（§六 给了三条候选路线的对比与启用条件）。

## 一、需求拆解：「图像检索」的三种含义

| | 含义 | 输入 | 输出 | 现在能做到吗 | 成本量级 |
|---|---|---|---|---|---|
| **① 文字找图** | 用词搜图版 | 文字 | 图版列表 | ✅ **数据已齐，只差索引** | 小（1.5 天） |
| **② 以图搜图** | 拿一张图找相似图 | 图片 | 相似图版 | ❌ 需向量模型 | 大（3–5 天 + 模型） |
| **③ 图版找文献** | 找含某图的文献 | 文字/图 | 文献 | ⚠️ 文献全文检索已有（`docs_fts`），图版只是**入口** | 小（接线即可） |

★ **本方案主力是 ①**，③ 顺带做；② 单列一档、可选、默认关闭。

## 三、方案总览

### 3.0 独立模块的边界（先划清，再动手）

| 维度 | 图像检索 E2（独立） | 文献检索 E1（现有） |
|---|---|---|
| 代码 | `lzkg/imgsearch/`（独立包） | `lzkg/db.py` + `lzkg/segment.py` |
| 索引 | **`img_fts` + `img_index_meta`**（自己的表） | `docs_fts` / `docs_seg` / `raw_json_fts` |
| 端点 | **`/api/imgsearch/*`**（自己的前缀） | `/api/search` `/api/literatures` … |
| 前端入口 | **独立页签「图版检索」**（`#/imgsearch`） | 检索页 `#/search` |
| CLI | `img-reindex` / `img-status` | `reindex` / `segment-status` |
| 判据 | **`tests/test_imgsearch.py`**（独立文件） | `tests/test_all.py` `test_segment.py` |
| 耦合 | 仅 `lit_id`（点图版 → 跳文献详情） | — |

★ **唯一的耦合点是 `lit_id`**：图版 → 文献 → 全文检索，这条链保留；
其余一律不共享（不共用清洗函数、不共用查询分流、不共用索引表）。

### 3.1 分三档

| 档 | 做什么 | 新增依赖 | 包体影响 | 默认 |
|---|---|---|---|---|
| **E2-0 文本图检索** | 图注 + AI 描述 + 图号 + 类型 → 新 FTS 索引；文字搜图 | **零**（SQLite FTS5 已有） | ~0 | **开** |
| **E2-1 标签反查 / 相似图** | 按四维标签找图、同标签相似图推荐 | **零**（`img_tags` 已有） | ~0 | **开** |
| **E2-2 向量层（以图搜图）** | CLIP embedding + 相似图 | 可选（onnxruntime + 权重） | **+400 MB 以上** | **关** |

### 3.2 三条总原则（继承本项目一贯纪律）

1. **文本来源唯一**：图版检索用的文本**只从库里已有字段来**
   （`caption` / `ai_desc` / `ai_objects` / `fig_no` / 类型标签），
   **不重新生成、不二次加工出第二套真值**。
2. **不引入第二套检索引擎**：FTS5 已经在用，图版索引继续用 FTS5；
   Whoosh / tantivy / Elasticsearch / 向量库一律不装。
3. **依赖可选化**：新增依赖必须**可选**（与 `jieba` 同款处理）：
   缺了**功能关闭并明写「未启用」**，**绝不能导致程序起不来**
   —— 这是 v3.9 换机闪退换来的教训：**硬依赖漏声明 = 换台机器就崩。**

## 四、E2-0 文本图检索（主力）

### 4.0 模块骨架（新增文件一览）

```
lzkg/imgsearch/
├── __init__.py      # 模块入口（对外只暴露 search / build_index / status）
├── clean.py         # 图注清洗：中英分列 / 全角归一 / AI 兜底句打标
├── index.py         # img_fts 建表与灌库（幂等，可重建，带版本与指纹）
└── api.py           # 端点：/api/imgsearch/search、/api/imgsearch/stats
```

★ 端点前缀用 **`/api/imgsearch/*`**，**不复用 `/api/images`**（那是既有「按 lit_id 取图版」的接口，
语义不同，混在一个前缀下迟早对不齐口径 —— E1 踩过 `mode` 一字段两套词表的坑）。

### 4.1 索引设计

新增表 `img_fts`（FTS5，**`tokenize='trigram'`** —— 与 `docs_fts` 同款，**子串友好**）：

| 列 | 内容 | 来源 |
|---|---|---|
| `img_id` | 图版号 | `images.img_id` |
| `lit_id` | 所属文献 | `images.lit_id` |
| `caption_raw` | 原始图注 | `images.caption`（清洗前留档，便于回溯） |
| `caption_zh` | 抽出的中文图题 | 由 `caption_raw` 清洗 |
| `caption_en` | 抽出的英文图题 | 由 `caption_raw` 清洗 |
| `ai_desc` | AI 描述（带质量标记） | `images.ai_desc` |
| `ai_objects` | AI 物体词 | `images.ai_objects` |
| `fig_no` | 图号 | `images.fig_no` |
| `img_type` / `obj_type` | 类型 | `images.img_type` / `obj_type` |

**分词器为什么选 trigram**：图版检索里两字词极常见（「玉琮」「城墙」「水坝」「神人」）。
trigram 索引不了两字词 → **沿用 `docs_fts` 已有的分流逻辑**：
token 长度 ≥3 走 `MATCH`，**含 <3 的 token 就整条退回 LIKE 扫 `img_fts`**（`img_fts` 只有 3162 行，LIKE 扫极快）。
**不重写一套新分流逻辑。**

### 4.2 文本清洗三条规则（本步主要工作量）

| 规则 | 做法 | 依据 |
|---|---|---|
| **R1 中英分列** | 图注形如 `图N 中文标题；Fig.N 英文标题`：**先 NFKC 归一**（全角→半角），再按 `；/;` 分段，**段内含中日韩字符归中文侧、否则归英文侧** | 实施后实测：中文图题 **2168（68.6%）**、英文图题 **1047（33.1%）**、两者都有 62 |
| **R2 AI 兜底句打标** | `ai_desc` 含「具体视觉细节以原图为准」→ 打 `ai_generic=1`，界面上标「AI 描述为通用表述」 | 实测 **273** 条。★ **只标记、不降权**（与复核同口径：非文本信号不干扰检索） |
| **R3 噪声剔除** | 中文侧剥掉「图N」前缀；**剥完没剩中文 = 只有图号没有图题 → 留空**（图号另有 `fig_no` 列）；英文侧剥「Fig.N」前缀并转小写 | 实施时发现：带 fallback 会把纯英文图注塞进中文列，**虚高 710 条**（见 §十一） |

★ **不做的事**：不修图注原文（源数据只读）、不改 AI 描述、不"纠正"错标图版
——**错配图版比缺图严重得多**（项目既有纪律）。

### 4.3 API 契约

```
GET /api/imgsearch/search?q=&mode=&dims=&img_type=&obj_type=&review=&page=&size=
GET /api/imgsearch/stats          # 索引行数 / 版本 / 指纹 / stale
```

返回：

```json
{
  "total": 0,
  "page": 1, "size": 20,
  "items": [{
    "img_id": "IMG-LIT-000001-8",
    "lit_id": "LIT-000001",
    "fig_no": "2",
    "caption_zh": "良渚古城遗址空间数据库整体设计图",
    "caption_en": "Diagram of the overall design of the spatial database",
    "ai_desc": "两幅并排的GIS软件界面截图…",
    "ai_generic": false,
    "img_type": "IMG-SCHEMATIC｜示意图",
    "obj_type": "IMGOBJ-OTHER｜其他",
    "review_status": "待人工复核",
    "review_verified": false,
    "thumb_url": "/media/img/IMG-LIT-000001-8.jpg",
    "hit_layers": ["caption_zh", "ai_desc"],
    "snippet": "…<mark>…</mark>…"
  }],
  "stale": false
}
```

**字段口径（不许混）**：

| 字段 | 含义 |
|---|---|
| `mode` | **只**表示档位：`exact`（子串）/ `both`（子串 + 标签命中）—— **不与"走 FTS5 还是 LIKE"混用**（那是 E1 踩过的坑：`mode` 一字段两套词表） |
| `exact_backend` | 精确层实际走 `fts5` 还是 `like` |
| `hit_layers` | 命中在哪些层：`caption_zh` / `caption_en` / `ai_desc` / `ai_objects` / `fig_no` / `tags` |
| `review_verified` | **是否人工核实过**（已人工核实 / REV-PASS → true） |

### 4.4 界面

| 位置 | 做什么 |
|---|---|
| **独立页签「图版检索」** | **单独一个入口**（`#/imgsearch`），**不塞进文献检索页**。缩略图网格 + 图号 + 图题 + **复核状态徽标** + 命中层级徽标 |
| **文献详情页** | 现有图版区保留（不改造）；**只在图版卡上加一个「在图版检索中打开」的链接**，用 `lit_id` 弱耦合过去 |
| **图版卡** | 缩略图（图走 `/media/img/`，沿用 `rawtext.py` 已有路径安全解析） |

★ 为什么**不**把图版做成检索页的一个分区：检索页现在是「文献」的专属界面，
加一个可切换的图版分区会让**两套命中逻辑共处一个页面**——用户分不清「这是搜文献还是搜图」，
后期维护也容易把口径搅在一起。独立页签代价是多一个入口，收益是**心智与代码都干净**。

★ **零外链**：缩略图一律走站内 `/media/img/`，**不上 CDN**。

### 4.5 判据（预写；实施时把数字换成实测真值）

新增 **`tests/test_imgsearch.py`**（独立文件，不塞进 `test_all.py`），
判据**必须等于实测真值**，不写「不为空」：

| # | 判据 |
|---|---|
| 0 | **模块独立性**：`/api/imgsearch/*` 与 `/api/search`、`/api/images` **不共用同一段查询代码**（静态扫 import 断言） |
| 1 | `img_fts` 行数 **== `images` 行数 == 3162** |
| 2 | 解析出中文图题的条数 == 现算真值（实施时填），且**每条都真的含非图号文字** |
| 3 | AI 兜底句标记数 == 现算真值（当前样本 273） |
| 4 | 查询命中数 **== 同条件在 Python 里现算的真值**（逐条对账） |
| 5 | 命中层级标记准确：只命中 caption 的条目 **不得** 标成命中 `ai_desc` |
| 6 | 图版检索结果**不泄露本机绝对路径**（只出站内 URL） |
| 7 | 两字词（「玉琮」）能命中（走 LIKE 兜底也算），**不得 500** |
| 8 | 复核徽标与库里 `review_status` **逐条一致** |
| 9 | 全量回归 **370 项仍全绿**（旧判据不重跑＝没做完） |

## 六、E2-2 向量层（以图搜图）—— 为什么"可选且默认关闭"

### 6.1 现实约束

| 约束 | 数值/事实 |
|---|---|
| 模型权重 | CLIP ViT-B/32 ONNX int8 ≈ **100–350 MB** |
| 推理依赖 | `onnxruntime` ≈ **150–200 MB**（还会带 numpy 等） |
| 对接包现体积 | **120.1 MB** → 加进来直接翻几倍 |
| 零外链原则 | 云端 API 不能作默认路径；本地权重要随包或用户自备 |
| 本机现状 | **无 torch、无 CLIP 权重** |

### 6.2 三条候选路线对比

| 路线 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **A. 本地 ONNX CLIP**（模型随包/用户自备） | 离线、隐私好 | 包体 +300~550 MB；换机要重新下模型 | **备选**，只做「用户自备模型」模式 |
| **B. 云端 embedding API**（复用已有"用户自带 key"） | 不占包体 | **图版图片要上传** → 流量 + 隐私 + 公网暴露风险；断网不可用 | **不推荐做默认**；可作为管理员自选的高级项 |
| **C. 纯文本图检 + 标签相似**（E2-0/E2-1） | 零依赖、离线、当天可上、判据好写 | 搜不出"画风相似但文字不同"的图 | **主力** |

### 6.3 结论与启用条件

- **E2-0/E2-1 落地前不动模型。**
- E2-2 只在满足**全部**下列条件时才做：
  ① 用户明确要「以图搜图」；② 能接受模型体积（**单独一个模型包**，不塞进对接包）；
  ③ 有一台机器可离线跑推理（向量索引与主库分离，可选启用）。
- **启用方式必须与 `jieba` 同款**：依赖与权重缺失 → **功能关闭 + 明确写「向量检索未启用（缺模型）」**，绝不 500、绝不影响站点启动。

## 九、明确不做什么

| 不做 | 为什么 |
|---|---|
| 把图版检索**塞进文献检索页**当一个分区 | 两套命中逻辑共处一页，用户分不清、口径迟早搅在一起（§4.4） |
| 图版检索**复用文献检索的查询代码 / 索引表** | 改一边弄坏另一边；独立模块才守得住（§3.0） |
| 把 1228 MB 图版塞进对接包或公开仓库 | **红线**：机构订阅件 + 包体会失控 |
| 装 Whoosh / tantivy / Elasticsearch / 向量数据库 | **两套索引 = 两套真值** |
| 默认开启以图搜图 | 体积、离线、隐私三重不满足（§六） |
| 用 AI 描述冒充人工复核 | 项目红线：错配比缺图严重 |
| 自动"修正"图注/图版错配 | 同上；校验不过就不改 |
| 给图版检索写第二套分词/分流逻辑 | 复用 `docs_fts` 那套（≥3 走 MATCH / 含 <3 退 LIKE） |

## 十、已知限制与风险

1. **复核覆盖率 19.6%** → 检索结果里 **79.7% 是待复核**。
   界面显示复核徽标（**已复核 / 待复核**）；报告里引用图版时**必须**注明复核状态。
   ★ **复核不参与检索**：不按它过滤、不降权、不排序（用户口径，见 §4.3）。
2. **中文图题解析率 68.6%**（实施期实测，3162 条里 2168 条能解析出中文图题）。
   剩下 31.4% 要么图注只有英文、要么只有图号没有图题 —— 英文那部分**多词查询命中不了**（源 PDF 抽取丢了单词空格）。
3. **AI 描述有 273 条兜底句 + 普遍粗粒度** → 靠 `ai_generic` 标记降权，不当主力。
4. **「其他」类型占 62.8%** → 类型筛选不足以定位，图版文本层必须做厚。
5. **图版只覆盖 174/200 篇（87%）** → 26 篇文献搜不到图版，不是 bug。
6. **图版路径在源目录 `04_专题研究/04_文献图像/`** → 对外一律走 `/media/img/`，
   **不暴露本机路径**（判据 6 盯着）。
7. **以图搜图（E2-2）没做** → 对外说明里要写明「本版不支持以图搜图」，
   **不能让人以为搜不到就是没有**。

## 十一、实施结果（2026-11-03 实测）

**E2-0 与 E2-1 已实施**（E2-2 向量层按 §六 保持**默认关闭**）。

| 项 | 实测 |
|---|---|
| 索引行数 | **3162**（== `images` 表行数） |
| 覆盖文献 | **174 篇** |
| 索引体积 | 3162 行 trigram 索引，**毫秒级** |
| 中文图题解析 | **2168 / 3162（68.6%）** |
| 英文图题解析 | **1047 / 3162（33.1%）**（两者都有 62） |
| AI 兜底句 | **273 条（8.6%）** |
| 判据 | `tests/test_imgsearch.py` **34 / 34**；全量回归 **404 项全通过**（177+31+30+97+35+34） |

**检索实测**：

| 查询词 | 文本＋标签（both） | 仅图版文本（exact） | 精确层 |
|---|---|---|---|
| 玉琮 | 160 | 160 | LIKE 兜底（两字词） |
| 遗址 | 1162 | 824 | LIKE 兜底 |
| 良渚文化 | **2170** | **126** | FTS5 |
| GIS | 146 | 19 | FTS5 |
| 空间数据库 | 12 | 12 | FTS5 |
| 神人兽面 | 59 | 59 | FTS5 |

**★ 与 v1.0 方案的三处偏差**（都因实测而改，不是缩水）：

1. **图题解析率从 38.4% 变成 68.6%** —— v1.0 用的是「朴素正则、不做全角归一」的口径；
   真正起作用的是 **NFKC 归一**。这说明方案里「清洗是主要工作量」判断对了，
   但低估了**全角字符**这一项。
2. **R2 降权改成只标记** —— 与「复核不影响检索」同一口径：**非文本信号不干扰检索**。
3. **分列判据从「按 Fig 标记切」改成「按段内有无中日韩字符」** —— 中间版本把纯英文图注
   塞进了中文列，解析率虚高 710 条，是判据「独立实现交叉验证」抓出来的。

**★ 一条方法论**：索引内部自洽 ≠ 口径正确。
本轮的 bug 恰恰是「索引和源数据逐行对账全过、接口数字也自洽」，
但**分列规则本身选错了边** —— 只有拿**另一套独立实现**现算一遍才能发现。
