### 1.5 AI 接口：三种协议，配置存在浏览器里

用户的要求是「**保存到浏览器，大家可以自行填写选择**」——即**每人带自己的 key**，
不共用一个服务端 key。好处是费用与额度各归各人、换模型不用改服务端。

| 协议 | 走向 | 鉴权头 |
|---|---|---|
| OpenAI 兼容 | `POST {base}/chat/completions` | `Authorization: Bearer <key>` |
| Anthropic | `POST {base}/messages` | `x-api-key: <key>` + `anthropic-version: 2023-06-01` |
| 本地 / 私有 | 同 OpenAI 兼容，**key 可空** | 无 |

- 协议清单从 `/api/ai/providers` 取，**前端不硬编码**
- 前端存 localStorage → 提问时随请求发给本机后端再转发给模型服务商
- **key 只在这一次请求里用完就走**：不落库、不写日志、不回显；错误信息里的 key 会被打码
- **边界要说清**：不能把「不落盘」说成「从未经过后端」——请求确实经过本机后端；
  且**同一台机器上的其他人能读到 localStorage 里的 key**，所以界面上写明「公用电脑上不要填」
- **降级**：没配或连不上 → 退回本地检索摘要，`degraded=true`，答案里明写「不是模型生成的回答」

**验收方式**：起一个**协议桩**（假服务）分别按三种协议应答，逐条核对
请求路径 / 请求头 / 请求体字段 / 响应解析，以及「key 没出现在回给前端的内容里」。

**权限两道**：界面层（非管理员看不到「提案与审核」整块）+ 接口层（管理端点一律
`require_admin`，手工构造请求也只得到 403）。

**「列名不能硬编码」这件事是真出过问题的**：前端原先内置的 22 个列名和真实列名对不上
（写的是「作者」，真实列叫「作者/责任者」；写的是「文献类型」，真实列叫「文献类型代码*」），
提交上去后端一个都认不出来。现在前端从接口取。

## 二、这一轮真正难的三件事

### 2.1 让图谱布局**可复现**（而且踩了两个隐蔽的坑）

**问题**：vis-network 默认的力导向是**每次打开都在重算**，节点位置会漂。
同一份数据两次截图对不上，报告里的图和演示时的图不是一张。
而且本图密度是参照项目的两倍（600 节点 / 7140 边），力导向下缩成一团毛线，点都点不中。

**做法**：后端一次把坐标算好存进 `graph_nodes.x / y`，前端 `physics:false` 直接用坐标画。
算法是**社区感知**的向日葵排布：

1. Louvain 分簇（seed 固定，与图分析用同一套参数）
2. 每簇在自己的诱导子图上跑 spring_layout
3. 簇之间沿**自适应螺线**外推，保证相邻簇不重叠
4. 全图归一到 `[-1000, 1000]`

**踩到的两个坑**（都是**不报错、同进程里测两次还是绿的**，只在「重算一次后和库里的坐标对不上」才暴露）：

| 坑 | 机制 | 实测后果 | 修法 |
|---|---|---|---|
| **SQLite 无 `ORDER BY` 时扫描顺序会变** | 优化器按统计信息在「走 node_id 索引」和「走表扫描(rowid)」之间自选；而 Louvain 与 spring_layout **都对节点插入顺序敏感** | 只是 UPDATE 了几行让优化器换了策略，社区从 **9 个变 8 个**，坐标最大差 **191** | 参与图算法的查询一律写死 `ORDER BY`（`graph.load_graph`） |
| **Python `set` 迭代顺序受 `PYTHONHASHSEED` 随机化** | `G.subgraph(社区集合).copy()` 在集合比原图小一半时按 **set 迭代顺序**建图；而 spring_layout 把初始随机位置按节点顺序分配 | 同一份数据**跨进程**坐标不同 | 建诱导子图时显式按 node_id 排序（`layout._induced_sorted`） |

**验收判据**（写进 `tests/test_all.py --layout`）：

- 「换 `PYTHONHASHSEED` 结果不变（跨进程可复现）」——**跨进程 + 换哈希种子**比对布局签名。
  只写成「同进程调两次一致」是**测不出上面两个坑**的。
- 「load_graph 扫描顺序已固定」
- 「每个节点都有布局坐标」3486/3486
- 实测：进程 A / 进程 B / 库内坐标签名完全相同（`d6ce8d6a6df01434`）；
  **全新迁移出来的库与增量库的布局也完全一致** → 换个环境重建，图的画法一模一样。

### 2.2 「仅本机」的限制，在隧道后面**等于没锁**

**问题**：`/api/health/detail` 这类端点含**本机绝对路径**（库在哪、源数据在哪），
挂公网等于送出一张地图。原来的判断是
`request.client.host not in ("127.0.0.1","::1")` → 403。

**但**：在 **Cloudflare Tunnel / 反向代理**后面，uvicorn 看到的直连方是
**代理进程本身**（隧道走本机回环）→ `client.host` **恒为 127.0.0.1**。
也就是说，这个「仅本机」的锁**在真正需要它的场景下完全不生效**。

**修法**（`app.py` 的 `_is_local_request`）：

1. 直连方地址**必须**是回环地址
2. **且**没有转发头，或转发来的地址（`CF-Connecting-IP` / `X-Real-IP` / `X-Forwarded-For`）
   也是回环

→ 隧道进来的公网访客：直连方回环 ✓、转发头是公网 IP ✗ → **403**
→ 外网直连：直连方是公网 IP ✗ → **403**
→ 本机直接访问：✓ → 放行

另加一道总闸：`config.json` 的 `app.local_detail`，挂公网时置 `false` 可整体关掉。

**验收方式**：`_tools/audit_exposure.py` 做**两遍**探测——普通匿名 + **「隧道视角」**
（带 `CF-Connecting-IP: 203.0.113.7` 模拟经代理进来的访客）。
隧道视角下本机端点必须全部 401/403。修之前实测 200（泄露绝对路径），修之后 403。

### 2.3 图谱的边必须给一条「列表通道」

cacx 实测过：画布缩到 0.27 时边只剩 19px、标签 2–3px，**点不中**。
本图密度是它的两倍。所以图谱页给了左侧 260px 的**边列表**：

- 数据源就是 `/api/graph` 已经返回的 `edges`，不额外发请求
- 按源 / 目标 / 关系 / 两端节点名过滤
- 点一行 → 查证据 → 右侧显示原始证据与「打开文献」入口
- **最多渲染 300 行**（7140 条全渲染会卡），底部写明「共 N 条，已显示前 300 条」

## 三、数据口径：三个必须说清的边界

### 3.1 四维标签的「代码」是族系代号 —— 已升级成**受控词表唯一码**

实测库里 **5 个码位下藏着 54 个不同名称**
（`S-0802`×18、`S-0801`×11、`S-0803`×9、`R-0199`×8、`S-0804`×8）。

→ 按代码归一会把「环太湖」和「文化创意」并成同一个东西，**而且界面上看不出来**。

**v3.1 的处置**：不再「保留码位 + 标不可靠」，而是改成真正的受控词表
（`lzkg/vocab.py` + `data/controlled_vocab_codes.json`）：

| 动作 | 内容 | 结果 |
|---|---|---|
| **唯一码位** | 5 个族系代号**全部退役**，其下 54 个词各拿一个唯一码（新段 `R-02xx` / `S-09xx`） | `multi_semantics_codes` 清零 |
| **同义归并** | 人工审定的保守白名单：`墓葬→墓葬考古`、`玉器→玉器研究`、`建筑技术→建筑研究`、`数字化传播→数字传播` | 受控词 120 → **115** |
| **组合拆分** | `凌家滩文化/红山文化` → 两个独立文化（斜杠是原表的写法，不是概念） | — |
| **明确不合并** | `数字化保护`、`水利与环境`、`吴越文化` —— 更具体或范围不同的独立概念，合了丢信息 | — |

→ **图谱节点仍按「名称」建**（`tag_id = dim:name`），所以校准**不改变图谱语义**，
  只有 4 组同义归并会真的减少节点（图谱 3491 → **3486** 节点）。
→ 归并白名单与码位表都是**可审阅的文件**，不是代码里写死的常量。

### 3.2 有复核日期 ≠ 已复核

图像表「复核日期」3162 行全非空（含未复核的行），但「复核人」只有 214 行有值。

→ 判定「已复核」**一律读 `review_status` 字段**，永远不要用日期。
→ 复核覆盖率按状态字段统计：已通过 619 / 待复核 2516 / 其他 27 → **19.6%**，
这个数字**显示在界面上**，并注明口径。

### 3.3 文献级与图像级的复核状态**不是同一套口径**，不能混算

实测原始登记表里：

- 文献级只有两个值：`REV-PENDING｜已审核`（127 条）、`REV-PENDING｜待审核`（73 条）
- 图像级是另一组值（`REV-PENDING｜待人工复核` 2130、`已人工核实` 405、`待复核` 373、
  `REV-PASS｜通过` 214 …）

→ 总览的覆盖率**明确注明按 `images.review_status` 统计**，**不与文献级混算**。

### 3.4 地图坐标：分两层，**实测坐标不编，区域代表点标明是示意**

国内地图拾取的坐标是**加密坐标**（高德 GCJ02 / 百度 BD09），论文里的坐标是 **WGS84**，
两套混用会引入**几百米的系统误差**——在探方、灰坑、城墙段的尺度上足以把点位画到隔壁地块。

所以坐标分两层，**两层的口径必须分开说**：

| 层 | 表 | 现状 | 精度 | 能不能当坐标用 |
|---|---|---|---|---|
| **遗址实测坐标** | `遗址点位表.xlsx` 的「点位表」 | 18 个候选遗址，**坐标全空** | 待补 | 补上才能当坐标用；来源必须是原始文献 |
| **区域代表点** | 同文件的「区域代表点」 | 12 个空间分区，其中 **6 个配了点** | 两位小数 ≈ **±1.1 km** | **只是示意**，说清「这个分区的文献大概在哪一带」 |

**区域代表点只给真正的地理区域**：

- 上图（6 个）：良渚古城、良渚遗址群、良渚全域、良渚博物院、环太湖、姚江流域
- 不上图（6 个）：跨遗址、中国综合、浙江综合、文化创意、数字化、参考案例
  —— 前三个是**比较口径/范围型分类**，后三个是**主题分类**，
  **给它们配一个点就是在编造位置**，所以一律不配

出图时同址点会**合并**（良渚那 4 个分区代表点几乎重合，不合并的话四个标签叠成一团读不出来），
图上写明「6 个分区合并为 3 个位置」。

→ 细化坐标以「点位表」为准，区域代表点只是过渡。

## 五之五、v3.3 新增：Web Dev —— 组员把自己的浏览数据存下来

### 5.13 要解决的问题

组员想保存**自己的浏览记录**。浏览记录天然是个人数据 → **不该上传服务器**，
但只放浏览器又换不了设备。于是给一条路：**存在自己浏览器 + 同步到自己网盘**。

### 5.14 做了什么

- **浏览记录**：`localStorage` 键 `lzkg.browse.v1`，在 `renderDetail` 里自动记一条
  （题名/年份/时间），上限 500 条、重复浏览只更新时间；可查看、清除、导出 JSON
- **Web Dev（WebDAV）**：工作台第 ⑧ 个界面，配置（服务器地址/账号/应用授权密码/文件名）
  存在浏览器（键 `lzkg.webdav.v1`），提供 **测试连接 / 上传 / 从 Web Dev 恢复**
- **后端**：`lzkg/webdav.py` + `POST /api/webdav/test|put|get`（**要求登录**）

### 5.15 三条边界（界面与文档里都写死）

1. 数据与凭据只在**使用者自己的浏览器**里，本站**不保存**任何人的 WebDAV 凭据
2. 但测试/上传/下载时，**密码会随请求经过本站后端**再转发给 WebDAV 服务器
   —— 浏览器直连会被 CORS 挡死，这是 WebDAV 的现实。后端**不落盘、不写日志、不回显**
3. 后端**只允许公网地址**：`lzkg/webdav.py` 有 **SSRF 防护**
   （私网/回环/链路本地/保留地址一律拒绝、不跟随重定向、响应上限 2 MB）

配置区固定挂着两个说明链接（用户指定的）：
[坚果云：第三方应用授权 WebDAV 开启方法](https://help.jianguoyun.com/?p=2064)、
[WebDAV 是什么 / 怎么用（知乎）](https://zhuanlan.zhihu.com/p/397069064)。

### 5.16 实测

★ 真实使用中暴露的两个问题（已修）

1. **上传 404**：坚果云**不允许直接往根目录写文件**，文件必须放在**已存在的文件夹**里
   （多方资料与实测一致：PUT 到 `/dav/x.json` 返回 404，不是 403/409）。
   → 新增「**存放目录**」字段（默认 `lzkg`），后端上传前 **MKCOL 自动建出它**；
   **测试连接改为测最终目标目录** —— 原先只测根目录，才会出现「测试通过、上传却 404」。
2. **「文件名不合法」**：浏览器下载后显示的是**完整路径**（`下载NDM\lzkg-browse.json`），
   用户直接粘进文件名框 → 前端**只取最后一段**，不再让人猜规则。

★ 顺带补的两条同步途径（用户提的「需要一些途径进行同步」）

## 五之六、v3.6 新增：阅读原文通道 + XML 协作格式

### 5.17 要解决的问题

用户提出两件事：

1. 「**没有阅读原文的窗口**」—— 详情页只能看摘要与图版，看不到全文。
   并补充：「建议文献界面给予阅读原文通道（PDF/Markdown），或许可以顺带这两个资源的下载」。
2. 「**似乎没有引入 XML 作为协作的一些事宜的东西**」——
   组员之间交换数据没有机器可读的格式。补充：「这个功能可以与导入功能联动一下」。

问卷确认了两个决定：**XML 两者都要**（交换 + 视图）；**原文通道全开**（登录与否都给）。

### 5.18 做了什么

**新增三个模块**：`lzkg/rawtext.py`（MD→安全 HTML + 图版重写）、`lzkg/xmlexchange.py`（XML 交换格式）、
`lzkg/api_raw.py`（五个端点）。

**五个新端点**：

| 端点 | 作用 |
|---|---|
| `GET /api/raw/{lit_id}/markdown` | 全文（后端渲染的安全 HTML）；`?download=1` 出附件 |
| `GET /api/raw/{lit_id}/pdf` | 原始 PDF（inline 内嵌）；`?download=1` 出附件 |
| `GET /api/literatures/{lit_id}/xml` | 单篇结构化 XML（视图） |
| `GET /api/export/xml` | 协作交换数据集（全库） |
| `POST /api/import/xml/preview` | 回传预检（**不写主库**） |

**界面**：详情页多一块「**阅读原文**」（PDF / Markdown / 两个下载 / 结构化 XML 五个按钮，
模态窗口共用）；工作台多一张卡「**⑨ 协作交换（XML）**」；导入面板加「方式」选择器（xlsx / XML）。

### 5.19 三个值得说的技术选择

**① PDF 用 `<iframe>`，不引 pdf.js。**
本站**零外链**是硬约束，pdf.js 要么走 CDN（破约束）要么自己 vendor（体积与维护成本）。
浏览器原生 PDF 阅读器本来就能内嵌、翻页、缩放、下载 → 一个 `<iframe>` 解决。已在真实浏览器窗口验过
（13 页，缩略图 + 正文齐全）。

**② Markdown 在后端渲染，前端不解析。**
前端解析 MD 要引库（外链）或自己写（漏 XSS）→ 后端把 MD 转成**白名单 HTML**
（只放行 `sub/sup/i/b/em/strong`，其余转义），前端只做 `innerHTML` 注入。

**③ XML 一套格式两处用。**
交换（导出 / 回传预检）与视图（单篇 XML）共用 `literature_to_xml()`，
命名空间 `urn:lzkg:literature:1`，**23** 个交换字段。一处定义、两处用，不会漂移。

### 5.20 图版重写：把 CDN 直链换成本地图版

MinerU 解析出的 Markdown 里，图片是**外部 CDN 直链** —— 断网就没图。
重写规则是**宁可留占位，绝不错配**：

1. MD 图数**必须等于**库里这篇的图数 → 否则**整篇不重写**
2. 按**出现顺序**一一对应
3. 再校验**图注文本**（MD 的 alt 与库的 caption 能不能对上）
4. 校验**明确不通过**的 → 不重写，插占位提示

★ 把 A 图安到 B 图上 = **造谣**，比缺图严重得多。

**实测快照（2026-10-31，全库 200 篇）**：图数相等 **50** 篇 / 不等 **17** 篇 /
无图 **132** 篇 / `md_path` 文件名过长导致 Windows 路径解析不到 **1** 篇（LIT-000082）。
LIT-000001：MD 14 图 / 库 14 图 → 重写 **12**、未匹配 **2**（那 2 张的库 caption 被登记成坐标文字）；
渲染后 12 个 `<img>`、0 字面 `![` 残留、**0 CDN 残留**。

### 5.21 「与导入功能联动」= 共用审核链路，不是另开后门

XML 回传**只做预检**：逐条报「哪些字段变了」，**绝不写主库**。
改动仍走「预检 → 管理员批准 → 入库」，与 xlsx 提案制**同一套审核语义**。
不存在「XML 直接改库」的口子。

**往返闭环实测**：导出 200 篇 → 改 1 条 `review_status` → 回传预检 →
报 **1 处差异 / 199 条无变化**，主库未动。

### 5.22 界面口径改了（不改就是在撒谎）

原文通道全开后，页脚「机构订阅件不得外传」**当场变成半假话**。
改成：「**站内提供原文通道，不代表获得对外传播授权；标注为机构订阅/限内部使用的条目，请勿外传**」。

这与 v3.4「改了数据流向必须回头改界面口径」是同一条纪律：
**动了数据流向，就搜一遍界面和文档里所有描述数据流向的句子。**

权限做成配置开关 `raw.access`（`open` / `login` / `oa_only`），收紧时**改配置不改代码**。

### 5.23 本轮修掉的坑

| 坑 | 表现 | 修法 |
|---|---|---|
| 图片替换放在转义**之前** | 自己生成的 `<img>` 被二次转义 → **图全不显示**（不报错，只是空白） | 顺序固定为「先转义、后替换」 |
| `MD_IMG_RE` 只认 `https?://` | 重写后的 `/media/img/...` 匹配不上 → 页面出现字面 `![image](...)` | 两种前缀都认 |
| 占位标记用 `<!-- -->` | 被转义成 `&lt;!-- --&gt;` → 后续正则匹配不到；且只换 URL 会留下 `![alt](` 半截源码 | 改用 `@@LZKG_IMG:xxx@@`，替换**整段**语法 |
| `filename="中文.pdf"` | latin-1 编码报错 → PDF 端点 500 | RFC 5987：`filename*=UTF-8''` |
| `api_raw` import `api_v2` | **循环依赖**（`app.py` 要 import `api_raw`） | `require_admin` / `require_login` 下沉到 `auth.py` |
| 导出复用 `_query_lits` 忘了 `all_rows=True` | 结果被 **100 条上限**压扁（不报错） | 传 `all_rows=True`；实测导出 **200 篇 / 3 883 636 字节** |

## 六、交接给下一位的三句话

1. **先跑 `python -m lzkg doctor`**，它会告诉你源目录、库、依赖各是什么状态。
2. **改登记表列**只改 `lzkg/schema/registry_columns.json`（单一事实来源），
   模板、迁移、导入、导出都从它来，**不要在别处硬编码列名**。
3. **改了图谱就跑 `python -m lzkg rebuild-graph`**（它会连带重算布局坐标）；
   **只重建图谱不重算布局，新节点没有坐标 → 一半固定一半漂，比全都不固定还糟**。
