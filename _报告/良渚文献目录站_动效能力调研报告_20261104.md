## 二、已安装的 Skill：逐份通读后的实际能力

全部安装到 `C:\Users\you\.agents\skills\`，各含一份 SKILL.md（无脚本、无依赖、纯提示词知识）。

### 1. find-animation-opportunities（9,948 B，已装）

**做什么**：在界面里「找该动的地方」，同时**否决不该动的地方**。

**关键机制——四道闸门**。每个候选必须依次通过：

1. **频率** —— 100+ 次/天 → **永久否决**（键盘触发的动作是「取消资格」而非「酌情判断」）；
   每天几十次 → 只允许「几乎察觉不到」的微动效；偶尔 → 标准动效；罕见/首次 → 动效预算都在这。
2. **目的** —— 必须能归入六类之一：反馈 / 空间一致性 / 状态指示 / 防止突兀变化 / 解释 / 悦目。
   「看起来酷」不在列表里，说不出目的 = 否决。
3. **速度** —— 有硬预算：按压反馈 100–160ms、提示气泡 125–200ms、下拉 150–250ms、
   模态/抽屉 200–500ms。**只有「慢才好看」的动效，直接不合格**。
4. **功能** —— 功能性、密集型界面上的装饰是有害的。用户正在读的数据不该为了好看而动。

**输出格式是硬性的**：Part 1 机会表格（每格都要写明确的曲线、时长、属性）、
Part 2 **必填的「否决清单」**（2–5 条，写清是哪道闸门否决的）、
Part 3 一段结论。整站最多 5–7 条建议。

**对本站的意义**：这是**四个里最该先用的**。它自带「节制」立场和否决机制，
恰好对冲「加动效就变吵」的风险。而且它是**只读**的——只出计划不改代码。

### 2. animation-vocabulary（13,606 B，已装）

**做什么**：把「那个弹出来会缩一下的东西」翻译成准确术语。

含约 90 条术语的词表，分 12 类：出入口 / 时序编排 / 移动变换 / 状态过渡 / 滚动 / 反馈交互 /
缓动 / 弹簧物理 / 循环常驻 / 打磨特效 / 性能 / 原则。

**输出规则很克制**：用词表里的原文描述（权威，不许自己改写）、近义术语要**辨析**、
没有完全对应的就明说「这是近似」，**不许编术语**。

**对本站的意义**：给沟通用。你说「那个从上往下淡入的」，它给你
**Slide in / Fade in / Scale in / Pop in** 的准确名与区别——避免各说各话，
也避免给别的 AI 提示词时用词不准导致它实现错效果。

### 3. animation-performance（14,491 B，已装）

**做什么**：诊断「动效掉帧」，保证每一帧都赶得上预算。

**核心是分层表**（成本差一个数量级）：

| 层级 | 属性 | 成本 |
|---|---|---|
| 仅合成 | `transform`、`opacity`（现代 Chrome/Firefox 也含 `filter`、`clip-path`） | 最便宜，浏览器独立成层 |
| 绘制+合成 | `box-shadow`、`border-radius`、`color` | 每帧重绘，但不用重新布局 |
| 布局+绘制+合成 | `width`、`height`、`padding`、`margin`、`top`、`left` | 最贵，一个元素长大能带动全页重排 |

**四类「看着对其实会掉帧」的陷阱**：

- 动**继承的 CSS 变量** → 每个后代每帧重算样式，内容越多越卡；
- 动 **blur()** → Safari 上极贵，动画中的模糊要压在 20px 内；
- 每帧 `setState` → 每帧重渲染，渲染本身就超预算（本站无 React，但同类陷阱在 JS 里一样成立）；
- `will-change` 滥用 → 每个提升的层都吃显存。

**铁律**：永不写 `transition: all`；每条修复都要**指名病因**；
「在我机器上很顺」不算验证结论。

**对本站的意义**：本站有 **3162 张图版**、图版网格、vis-network 图谱（Canvas），
一旦加动效，掉帧不是理论风险。**这个 Skill 应该全程开着**，不是最后才查。

### 4. animate（11,829 B，**已装但未启用**）

**做什么**：从零把一个动效写出来，是前三个的下游。

决策顺序被明确定义：**该不该动 → 什么目的 → 用什么工具 → 动哪些属性 → 什么曲线与时长 → 怎么被打断 → 怎么退出**。
写出来的代码要能扛得住 `review-animations` 的审查。

**说明**：它是「构建」环节，本次先装上备用，等方案定了再启用。

## 三、本站实地勘察：现在有多少动效？

**几乎没有。** 全文 `index.html`（约 26.6 万字符）里与动效相关的只有这些：

| 位置 | 现状 |
|---|---|
| `.spin` + `@keyframes sp`（约 313 行） | 唯一一条真实动画：loading 旋转，0.8s linear infinite |
| `.legend .dia`、`.lz-legend .sw.st`、`.lz-mk-region.lz-hl span` | 静态 `transform: rotate(45deg)` / `scale(1.35)`，是**造型不是动效** |
| `network.fit({ animation: false })`（两处） | **主动关掉了** vis-network 的自带动画 |
| 全站 | **没有任何一条 `transition`** |

结论：这不是「动效做得不好」，是**根本没有动效**。所以三个 Skill 的适用面
不是「审查旧代码」，而是「从零建立并一开始就设好规矩」。

### 已经存在的动效接缝（真实代码位置）

| 位置 | 现象 | 接缝类型 |
|---|---|---|
| `#tabs` 页签切换（约 959 行） | 直接改 `location.hash`，页面瞬间换内容 | 状态切换缺过渡 |
| `view.innerHTML = ...`（数十处，如 1099/1216/5380） | 整页内容瞬间替换 | 内容突变 |

| 图版网格 ⇄ 列表切换（`#im-view`，本轮新加） | 两种 DOM 结构硬换 | 内容突变 |

## 五、按 Skill 的方法论，给本站的动效方案

> 以下**不是最终方案**——按你说的，等找到具体参考网站再定。
> 但这是 Skill 方法论跑出来的**初筛**，可以直接当讨论底稿。

### 5.1 先划定「不动的区」

Skill 的第一道闸门是频率与功能，本站有三个区域**天然出局**：

- **文献结果列表**（每天要看几十次、用户在读数据）→ 列表项**不许入场动画**。
  这正是 Skill 说的「数据不该为了好看而动」。
- **页签切换**（每天几十次）→ 只允许「几乎察觉不到」的过渡；
  **不能**做成整页飞入。Skill 对键盘/高频触发是「取消资格」级否决。
- **图谱（vis-network）** → 节点量级大的图，任何逐节点入场都会卡；
  Skill 对「功能图表上的装饰」明确判否。

### 5.2 通过闸门的候选（初筛，待与参考站对齐）

| # | 位置 | 现状 | 目的 | 频率 | 建议动效（初稿） |
|---|---|---|---|---|---|
| 1 | `.segbtn` 状态切换 | 类名硬切 | 状态指示 | 几十次/天 | 背景色过渡 150ms ease-out；**只动 background-color**，不动布局 |
| 2 | 按钮 `:active` | 无按压反馈 | 反馈 | 几十次/天 | `transform: scale(0.97)` + `transition: transform 160ms ease-out`，接近察觉不到 |
| 3 | `#lb` 大图查看器 | `display:none↔block` 硬切 | 空间一致性 | 偶尔 | 遮罩淡入 200ms；图片 `scale(0.96→1)` + 淡入 200ms ease-out，**从点击的缩略图位置为原点**（origin-aware） |
| 4 | `.modal` 遮罩与盒子 | 硬切出现 | 空间一致性 | 偶尔 | 遮罩淡入 180ms；盒子 `scale(0.97→1)` 180ms ease-out |
| 5 | loading → 结果 | 内容瞬间替换 | 防止突兀变化 | 每天几十次 | 结果区 `opacity 0→1` 120ms；**不做骨架屏**（本站数据到位很快，骨架屏反而是噪音） |
| 6 | 壁纸切换 | class 硬换，整站配色瞬变 | 状态指示 | 罕见 | 配色过渡 250ms（注意：**只过渡 color/background-color/border-color**，不要过渡全部属性） |
| 7 | 空状态 `emptyBox` | 瞬间出现 | 防止突兀变化 | 偶尔 | 淡入 150ms |

### 5.3 明确否决的（Skill 要求写进报告）

| 位置 | 否决理由 |
|---|---|
| 文献结果列表逐条入场 + stagger | **频率**：每天看几十次；**功能**：用户在读数据，装饰有害。Skill 明令否决 |
| 页签切换整页飞入/滑动 | **频率**：高频；Skill 对高频动效只允许「几乎察觉不到」 |
| 图谱节点逐个入场 | **功能**：功能性图表，且节点量级大，会卡 |
| 卡片 hover 时上浮 + 阴影放大 | **性能**：`box-shadow` 动画每帧重绘；改用 `transform: translateY(-2px)`，或用 `filter: drop-shadow()` 且需实测 |
| 打字机效果显示题名 | **目的**：说不出六类目的中的任何一类；纯装饰 |
| 页面加载时全站元素依次浮现 | **频率 + 目的**：像营销页，检索工具不需要 |

### 5.4 性能底线（来自 animation-performance）

1. **只动 `transform` 和 `opacity`**。需要动 `width/height/margin` 的，一律改写成 `scale/translate`。
2. **永不写 `transition: all`** —— 必须逐个列出属性。
3. 动效期间页面可能正忙（切页签时正在取数）→ **优先用 CSS transition**，
   不要用 JS 的 `requestAnimationFrame`（后者跑在主线程，会被数据加载挤掉帧）。
4. `will-change` **只在实测看到位移或掉帧时才加**，且只加在真正在动的元素上，不能加在 `*` 或大容器上。
5. `prefers-reduced-motion` 必须处理（减缓，不是归零）。
6. hover 动效要用 `@media (hover: hover) and (pointer: fine)` 圈起来，避免触屏上点了没反应。
7. **本站特有风险**：`--bp-*` 是**继承的 CSS 变量**。若动效去改这些变量，会触发全站后代每帧重算样式
   —— 这正是 Skill 点名的第一号陷阱。**动效只能动具体元素的 transform/opacity，绝不碰壁纸令牌。**

## 七、已知限制与风险

- **本报告是初筛，不是最终方案**。明确说「等找到具体参考网站再安排」，所以第五节的数值全是初稿。
- **Skill 的数值来自 Emil Kowalski 的设计工程哲学**，与本站的「博物馆图录」气质是否合，
  需要用本站自己的壁纸再验一遍；例如 Skill 偏好 200–500ms 的模态动效，本站走「克制」路线，
  可能要压到 180ms。
- **未验证**：本报告没有实测任何动效的帧率。第五节里所有时长都是 Skill 给的**建议值**，不是本站实测值。
- **`improve-animations` 与 `review-animations` 未装**：前者适合批量规划、后者适合事后把关，按需再装。
- **本站的零外链约束不受影响**：以上全部动效都是原生 CSS，无 JS 库、无 CDN。
- 现有唯一动画 `.spin`（loading 旋转）保持不变，它是**必要的状态反馈**，不属于「多余动效」。
